01

调试器在做什么

按下 Debug 按钮时，Rider 并非普通地启动程序，而是以调试身份创建进程。此后每当进程发生值得汇报的事件——加载模块、创建线程、触发异常、命中断点——操作系统会冻结该进程的全部线程，并将事件投递给调试器。

Debug 窗口里看到的一切，都是在这个"全世界都停住了"的窗口期内，由调试器反过来读取目标进程的内存与寄存器得到的。调试器处理完毕后通知系统继续，线程才重新运行。

可用调试的三个前提

把机器码还原成源代码行、变量名和类型，依赖三样东西，缺一不可。

前提说明缺失时的表现
调试信息Windows 上是 .pdb 文件，记录机器码地址与源文件行号的映射、变量在栈上的位置、类型布局只能看到汇编与裸地址，Variables 中全是问号
未优化的构建Debug 配置关闭优化，保证每条语句边界清晰、局部变量落在栈上单步乱跳、变量显示 optimized out、内联函数整个消失
二进制与 pdb 匹配可执行文件中记录了 pdb 的路径与一组 GUID，加载时逐一核对断点显示为空心，提示"不会被命中"

03

断点

在编辑器行号左侧的装订线上单击可添加行断点。按 Ctrl+Shift+F8（IntelliJ 键位）或 Ctrl+Alt+B（Visual Studio 键位）打开 Breakpoints 窗口，集中管理全部断点。

类型

左侧树按类型分组，列出的是 Rider 支持的全部语言的断点类别，与当前项目语言无关。

类型作用

C++ Exception Breakpoints不绑定代码行，绑定"C++ 异常被抛出"这一事件。勾选 When any is thrown 后，程序在 throw 的瞬间暂停
Low-Level Exception
Suppressions		抑制清单，方向与其他项相反：列出的低层异常调试器不暂停，直接放行
Symbolic Breakpoints按符号名（函数名）下断，无需定位到具体文件行
Method Breakpoints在函数入口处暂停
CLR / JavaScript /
CMake / GDScript		分别面向 .NET、前端、CMake 构建和 Godot 项目。在 C++ 项目中不会触发，默认勾选状态可忽略

异常断点的价值在于时机。它在 throw 发生的一刻暂停，此时调用栈尚未展开，抛出点及其全部上层调用连同各自的局部变量都还在 Frames 中。而在 catch 块里下行断点时，栈已经回退到捕获所在的层，中间的帧连同现场一并消失，只剩一个异常对象。

日志断点

取消 Suspend execution，配合三个 Log 选项，断点即成为纯观测手段：程序全速运行，Console 中留下完整轨迹。三个选项可叠加，输出形如：

Breakpoint reached: scenarios.cpp:94
i+i = (int) 12
Stack:
    Scenario02_Breakpoints() scenarios.cpp:94
    RunScenario(int) scenarios.cpp:372
    main(int, char **) main.cpp:58

调查执行成千上万次的循环，或时序敏感的多线程问题时，这比逐次暂停高效得多，且不会因暂停而改变线程时序。

Hit count 的运算符

勾选 Hit count 后，左侧是运算符下拉框，右侧填数字。运算符决定语义：

运算符含义
== 10仅在第 10 次命中时暂停一次，其后不再暂停
Is a multiple of 10第 10、20、30… 次命中时均暂停

Condition 与 Hit count 是串联关系。命中计数器统计的是「Condition 为真的次数」，而非该行被执行的次数——条件为假时计数器不递增。

因此 Condition: i == 42 配合 Hit count: == 10 永远不会命中：条件在循环中仅为真一次，计数器到不了 10。这不是缺陷，而是两个值组合描述了一个不存在的事件。

04

Threads & Variables

Debug 窗口的主标签页。左半部分是线程与调用栈，右半部分是变量。

栈帧（Frames）

左侧列表即调用栈，每一行是一个栈帧。顶行是当前正在执行的函数，向下依次是它的调用者，最末行通常是 main。它回答的是：程序是经由怎样的调用路径抵达当前这一行的。

原理

每个线程拥有一块连续的内存作为调用栈，从高地址向低地址生长。调用一个函数时，返回地址与参数被压入栈，函数在栈上为自己的局部变量划出一块空间——这块空间就是该函数的栈帧。函数返回时，这块空间被释放。

由此产生两个对调试极为重要的性质：

  • 每一帧的局部变量彼此独立。递归调用中，同一个函数的每一层都持有自己的一份局部变量——它们只是恰好同名，彼此毫无关系。逐帧点击 Frames，Variables 会随之切换到该帧的那一份。
  • 调用路径完整保存在栈上。调试器沿着栈帧逐层回溯，即可重建整条调用链。这就是 Frames 面板内容的来源。

崩溃或异常发生时，"当前这行代码"往往不是原因，"谁用什么参数把程序调到这里"才是。这个答案完整写在 Frames 里，因此它应当是暂停后第一个查看的面板。

使用

  • 单击任意一帧，Variables 切换到该帧的局部变量，编辑器同步跳转到对应源码行。这不改变程序状态，只是换个视角观察。
  • 帧行右侧的灰色斜体 文件:行号 指明该帧当前停在何处。
  • 执行 Step Out 后，Variables 顶部会临时出现 Return Value 一项，为刚返回的函数的返回值。
  • 顶部的线程下拉框用于切换线程。切换线程后整个 Frames 列表会完全更换——每个线程有各自独立的栈。

Variables

显示当前选中帧中可见的变量。结构体、std::vector、std::map、智能指针均可逐层展开，Rider 对标准库容器做了美化显示，呈现的是元素而非内部节点结构。

数据断点

普通断点绑定代码位置，数据断点绑定一块内存——该内存被访问时暂停，不关心是哪一行代码所为。它回答的是"是谁改了我的变量"，对于数组越界、野指针写入这类代码中根本没有任何一行提到被改坏的变量的问题，是唯一有效的手段。

必须先有具体的变量实例才能设置，因此流程固定为：先在某个断点暂停 → 在 Variables 中右键该变量 → Add Data Breakpoint。

Access Type触发时机
Write写入时触发。默认值
Read读取时触发
Any读或写均触发

默认的 Write 档只认写入，读取被完全忽略。触发时该次写入已经完成，因此看到的是新值，而 Frames 第一行即是执行该次写入的调用。同时存在的数据断点数量有上限，调查完毕后应及时删除。

Watches 与表达式求值

Variables 显示的是当前帧中恰好存在的局部变量；Watches 显示的是自行定义的表达式，每次暂停自动重新求值，并跨越不同的暂停点持续存在。

它并非变量查看器，而是一个在目标进程中执行的 C++ 表达式求值器。可用的表达式形式包括：

表达式用途
sizeof(a)/sizeof(a[0])数组元素个数
arr[2] + arr[3] + *p索引、解引用与算术混合
hp > 50 && color == Blue复合布尔条件，枚举可直接比较
scores.size()调用容器成员函数
*(int*)&pattern[0]按其他类型重新解释同一段内存
Compute(3, 1)调用函数，该函数会真实执行

求值只能调用当前模块内的函数。可执行文件自身的函数可以正常调用并真实执行，而它所依赖的 DLL 中的函数会失败，报错为 Identifier is not available, possibly due to compiler optimizations——该提示具有误导性，实际原因是跨模块，与优化无关。这一限制只属于求值器，程序自身跨模块调用不受影响。

求值会产生真实副作用。调用会修改状态的函数，程序状态就真的被改变，且无法撤销。调查问题时应尽量只求值无副作用的表达式。

另：Watch 按当前选中的帧求值。切换帧后表达式可能变为错误提示，这未必是表达式有误，也可能只是当前帧中不存在该标识符。

Watch 与断点 Condition 接受相同的表达式语法。调试复杂条件时，宜先在 Watch 中确认表达式返回值符合预期，再复制进 Condition。

Parallel Stacks

Variables 旁边的第二个标签页。Frames 一次只能显示一个线程的调用栈，Parallel Stacks 把所有线程的调用栈画在同一张图上。

核心机制是合并：调用路径完全相同的多个线程折叠成一个节点，节点顶部标注线程数（如 2 threads）。路径出现分歧的位置即节点分叉处。

因此这张图直接呈现的是线程行为的分布：哪几个线程在做同一件事、哪一个走了不同的路、有没有线程卡在意料之外的位置。线程数一多，逐个切换 Frames 排查的成本极高，而此图一眼可见。带 ✓ 标记的是当前选中的线程。

05

Console

被调试程序的标准输入输出。printf、std::cout 的内容在此显示，需要键盘输入的程序也在此输入。

日志断点的输出同样汇入此处，因此调查过程中 Console 常常同时承载程序自身的输出与调试器的观测记录。

若程序在断点处暂停时 Console 看不到本应已经打印的内容，通常是标准输出缓冲所致，与调试器无关。控制台程序可在启动时关闭缓冲：

std::setvbuf(stdout, nullptr, _IONBF, 0);
06

Memory View

按地址显示原始内存。Variables 给出的是「编译器认为这块内存是什么」，Memory View 给出的是「这块内存实际上是什么」。二者不一致时，问题就在其中。

典型用途：缓冲区越界、结构体对齐、字节序，以及怀疑类型被误用的场合。

三栏读法

栏说明
地址栏每行 16 字节，故行首地址末位恒为 0，相邻两行相差 0x10。行内第 n 个字节的地址等于行首加 n
十六进制数据区每两个字符为一个字节。其间的空格仅为每四字节分组以便计数，无语义
ASCII 预览把每个字节当作字符显示，不可打印者以 · 代替。查看字符串时有用，查看数值时应忽略

顶部 Go to 接受表达式，填入 &变量名 即可定位。也可直接粘贴地址。

十六进制

内存视图一律使用十六进制，原因在于 16 = 24：一位十六进制恰好对应四位二进制，两位即一个完整字节。用十进制显示会丢失这种对齐关系。

换算按 16 的幂展开，两位数的快速算法是左位 × 16 + 右位：

0x64  =  6 × 16 +  4  =  100
0xC8  = 12 × 16 +  8  =  200
0xFF  = 15 × 16 + 15  =  255

其中 A–F 代表 10–15。与二进制换算则按四位一组直接拆分：1101 1010 → D A → 0xDA。

小端序

x86/x64 采用小端序：多字节数值的低位字节存放在低地址。因此从内存拼回数值时必须倒序读取。

内存顺序（低地址 → 高地址）：  64  54  00  00
数值顺序（高位 → 低位）：      00  00  54  64  →  0x00005464 = 21604

内存中不存在「类型」，只有字节；类型是编译器施加的解释规则。同样这四个字节 64 54 00 00：按 32 位整数读是 0x00005464（21604），按两个 16 位整数读是 21604 和 0，按 C 字符串读则是 "dT"（0x64='d'，0x54='T'，随后是结束符）。字节未变，变的只是解释方式。

注意字符数组不倒序——它按地址顺序逐字节排列。倒序只发生在多字节的单个数值上。

内存对齐

以下结构体四个字段合计仅 14 字节，而 sizeof 为 24。多出的 10 字节称为填充，由四条规则决定。

struct Padded {
    char   tag;    // 偏移 0
    int    id;     // 偏移 4
    char   flag;   // 偏移 8
    double value;  // 偏移 16
};                 // sizeof == 24
#规则
1每个类型有其对齐要求，标量类型通常等于自身大小：char 1、short 2、int 4、double 8、指针 8
2每个成员必须置于其对齐值的整数倍偏移上。对不齐则向后跳，跳过的字节成为填充
3结构体自身的对齐值等于成员中最大的那个
4sizeof 必须为结构体对齐值的整数倍，不足则在尾部补齐
偏移内容依据
0tag对齐 1，从头放置
1–3填充 3 字节下一成员 int 对齐 4，1/2/3 均非 4 的倍数
4–7id4 是 4 的倍数
8flag对齐 1，紧接放置
9–15填充 7 字节下一成员 double 对齐 8，9 至 15 均非 8 的倍数
16–23value16 是 8 的倍数

填充永远是为下一个成员（或结尾）服务的，与它前面那个成员无关。flag 后有 7 字节填充，并非 flag 需要，而是其后的 double 必须落在 8 的倍数上。

由此可得一条实用结论：调整字段顺序可减少填充。同样这四个字段，按 double, int, char, char 声明时 sizeof 为 16，比原顺序节省三分之一。经验法则是按对齐要求从大到小声明。

填充字节从未被写入，其值未定义。因此不可用 memcmp 比较结构体（字段相同的两个对象可能因填充内容不同而判为不等），也不可将结构体按字节直接写入文件或网络包。

07

Debugger Output 与 Modules

Debugger Output (LLDB)

调试器后端本身的日志，而非被调试程序的输出。Rider 的 C++ 调试基于 LLDB，此处显示 LLDB 的原始消息：符号加载情况、断点解析结果、后端报出的错误等。

日常调试无需关注。它的价值在于调试器本身行为异常时——断点无法绑定、符号加载失败、求值报出难以理解的错误——此处往往有更具体的原因。

Modules

列出当前进程已加载的全部模块（可执行文件与动态库），并标明各自的符号加载状态。

用途集中于一点：确认某个模块的调试信息是否成功加载。「断点为什么是空心的」「为什么进不去这个函数」，多数能在此处得到答案——若该模块符号未加载，其中的代码便无法按源码级别调试。
