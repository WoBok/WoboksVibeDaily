延迟渲染 与 前向渲染

同一套 PBR 参数、同一个 BRDF、同一批阴影贴图。两者不是两种光照理论， 而是两种组织光照计算的调度方式。

核心命题 任何渲染器都必须让两组数据在某一刻相遇：几何/材质属性（随物体数量增长）与 光照信息（随光源数量增长）。
前向让它们在着色器寄存器里相遇 —— 画物体的当场算完； 延迟让它们在显存里相遇 —— 先把表面属性写进 G-Buffer，之后按屏幕像素统一打光。
MSAA、半透明、带宽、Lumen / Nanite / VSM 的可用性 —— 后面所有差异，都是这一个选择的必然推论。

01

同一个问题：一个像素怎么变亮

The convergence problem

实时渲染器的核心循环，本质上是在每个像素上求解这个式子：

最终颜色 = 自发光 + 间接光 + Σ光源 [ 光色×强度 × 阴影可见性 × BRDF(材质属性, L, V) × max(N·L, 0) ]

要算出它，必须在同一时刻握有两组来源完全不同的数据：

数据组来源增长维度
几何 / 材质属性
Normal · BaseColor · Roughness · Metallic · Specular · ShadingModel		 顶点 → 光栅化 → 材质图求值 由物体决定，随几何复杂度增长
光照信息
位置 · 颜色 · 衰减 · 阴影贴图 · IES · LightFunction		 场景光源列表 + 阴影 Pass 由光源决定，随灯数增长

两条数据流必须交汇。交汇点选在哪里，就决定了你在用哪种渲染路径。 切换下面的开关，看同一批数据在两种调度下走的不同路线。

「延迟」不是把渲染推迟到下一帧，而是把光照计算推迟到可见性已经确定之后。 深度测试筛完，屏幕上每个像素只剩唯一一个可见表面，此时再打光，每像素只打一次。
02

前向渲染

Forward · 在看见表面的当场把光算完

朴素前向与它的三个死因

for each 物体:
    for each 影响它的光源:        ← 由 CPU 侧提前绑定到 draw call 上
        算 BRDF，累加
    输出最终颜色

这是图形管线最直观的形态，也是最早被放弃的形态：

  • 复杂度是乘法：O(物体 × 光源)，灯一多就崩。
  • Overdraw 直接浪费光照：一个后来被遮挡的像素，它跑过的所有 BRDF 全部作废。
  • Shader 变体爆炸：光源要在 CPU 侧绑到每个物体的 draw call 上，「材质 × 灯数 × 阴影类型」的排列组合会把 shader 编译时间和内存吃光。

但被淘汰的是朴素前向，不是前向本身。现代前向是 Forward+ / Clustered Forward， 它借用了延迟渲染最精华的思路 —— 先剔除，再着色 —— 但剔除的是光源而不是几何。

Forward+：把光源剔除到视锥网格里

【Pass 1】 Depth Prepass（强制） ────────────────▶ 拿到完整深度缓冲
【Pass 2】 Light Culling（Compute Shader）
           把视锥切成 froxel 网格，每盏光源投影到它覆盖的 cell，写入光源索引表
【Pass 3】 BasePass · DepthTest = Equal
           每像素：① 由 (x, y, depth) 算出所属 cell 索引
                   ② 读该 cell 的光源列表（通常个位数）
                   ③ for 这几盏灯：采样阴影 + 算 BRDF + 累加
                   ④ 直接输出最终颜色到 SceneColor ← 一次性完成

复杂度回到 O(物体 + 像素 × 每格光源数)，而每格光源数通常是个位数。 Forward+ 能处理成百上千盏光源 —— 光源数量早就不是前向渲染的瓶颈了。

Depth Prepass 在前向里是正确性前提

前向的 BasePass 内含完整光照循环，一次 overdraw 浪费的是全部 BRDF 求值。 所以必须先跑一遍只写深度、不跑像素着色的 Prepass 把深度缓冲填满， 再让 BasePass 用 DepthTest = Equal、深度只读，保证每个像素只被着色一次。

代价是几何要提交两遍：顶点着色、剔除、draw call 全部翻倍。 这是前向渲染的隐性成本 —— 它把「像素侧的浪费」换成了「几何侧的重复」。

四项白送的能力

因为 BRDF 是在像素着色器里、在寄存器上算完的，几件事顺理成章：

能力为什么是免费的
MSAA 原生可用 输出的就是最终颜色。硬件多重采样平均的是颜色（线性可加）， 而不是材质参数（BRDF 的非线性输入）—— 不存在延迟路径那个悖论（见 5.1）。
带宽极小 没有中间缓冲，只有一个 SceneColor + Depth。在移动端的 TBDR GPU 上， 整个 tile 的渲染可以完全在片上内存里完成，一次都不回写主存。
材质模型完全自由 不需要把属性塞进固定通道。三层各向异性、自定义能量守恒项、任意风格化项 —— 随便写。
精度更高 不需要压缩法线、不需要从深度反推位置，没有编解码损失。
材质、光照、阴影、反射的逻辑全部集中在同一个巨型 shader 里：shader 变体多、编译慢、纹理采样器紧张、 寄存器压力高、occupancy 低。而且分簇剔除只能排除无关光源 —— 如果 30 盏灯确实同时照到一个像素，这个像素仍然要老老实实算 30 遍。
03

延迟渲染

Deferred Shading · 先看见表面，再给表面打光

插入一层存储，把乘法拆成加法

【Pass 1 · 几何】 几何 → 光栅化 → 深度测试 → 运行材质图 → 写出「这个像素的表面长什么样」
                                                            ↓
                                                   G-Buffer（显存 · MRT 多渲染目标）
                                                            ↓
【Pass 2 · 光照】 遍历光源 → 读 G-Buffer → 重建世界坐标 → 算 BRDF → 加法混合累加进 SceneColor
O(物体数 × 光源数) ──────▶ O(物体数) + O(受影响像素 × 光源数)

因为几何 Pass 带深度测试，只有最终可见的那一个表面会留在 G-Buffer 里 —— overdraw 依然会浪费材质图求值，但对光照的浪费被彻底消除了。这就是「延迟」二字兑现的地方： 把光照推迟到可见性确定之后。

还有一个常被忽略的收益：光照 shader 只需要写一份。它面对的是统一格式的 G-Buffer， 不再需要知道这个像素来自哪个材质 —— 材质系统与光照系统在代码层面解耦了， 前向那种「材质 × 灯数 × 阴影」的变体爆炸随之消失。

G-Buffer 里必须存什么

答案由 BRDF 的输入决定：法线、反照率、粗糙度、金属度、高光度、着色模型、深度。 下面是一个真实引擎（UE5）的具体布局 —— 它的价值不在于记住通道分配， 而在于看清固定布局会带来什么约束。点击任意一行展开。

四个细节解释了延迟渲染的绝大多数「怪癖」：

① 不存 Position

世界坐标由 屏幕UV + 深度 + 逆投影矩阵 反推。存 1 个 float 而不是 3 个 —— 这是延迟渲染最重要的单项带宽优化，代价是精度绑定深度缓冲的非线性分布。

② 着色模型只是一个 ID

几个 bit 的枚举，光照 Pass 靠 switch(ShadingModelID) 分支到不同 BRDF。 这是延迟渲染支持多种材质的唯一机制。 UE5 给它 4 bit，16 个槽位已用掉 14 个。

③ 自定义数据是复用通道

同一组通道的含义随着色模型漂移：清漆存层强度，次表面存散射颜色，头发存切线偏移。 直接推论 —— 同一个像素只能是一种着色模型。这是固定布局最硬的约束。

④ 几何 Pass 几乎不打光

唯一例外是自发光与预烘焙的间接光（被压进一个通道）。 所有动态光都留到下一遍 —— 这正是这个 Pass 便宜、能扛 overdraw 的原因。

光照 Pass 的三种组织方式

拿到 G-Buffer 之后，「怎么把光源喂给像素」还有三种做法，成本差异很大：

方式做法适用
代理体积
Light Volumes		 为每盏灯画出它的影响体积（点光画球、聚光画锥、方向光走全屏）， 让光栅化器 + 深度边界测试替你剔除。每盏灯一次 draw。 灯少，或每盏灯要绑不同的阴影贴图 / 光照函数资源 —— 无法批处理的灯只能走这条
分块
Tiled		 屏幕切 2D 块，每块求深度范围，剔出相关光源列表，一个 Compute Shader 打完。 通用，但深度跨度大的块（如天空与近景交界）剔除效率骤降
分簇
Clustered		 就是 2.2 那张 froxel 网格 —— 3D 剔除，避免了分块的深度跨度问题。 大量无阴影局部光的最优解

三种做法都依赖同一个数学前提：光照满足叠加性，所以每盏灯的贡献可以用 加法混合独立累加进 SceneColor，谁先谁后无所谓。

光源不是免费的，阴影往往比光源本身更贵。 一盏不投影的点光只是几行 BRDF；一盏投射实时阴影的光要从光源视角额外绘制一遍场景。 「延迟渲染擅长大量动态光」说的是直接光照的组织方式，从来不意味着大量实时阴影会变便宜。
这也解释了为什么真实引擎里总有一条「无法批处理」的慢路径： 有阴影贴图、有光照函数、有接触阴影的光源没法塞进统一的分簇 shader，只能一盏一盏画。

G-Buffer 真正的价值：一张全屏场景描述

这一点比「支持很多光源」重要得多，也是延迟渲染在今天仍是主流的真正原因。

G-Buffer 是一张全屏、逐像素、包含完整表面属性的场景描述。 一旦你有了它，一整个算法家族才成为可能 —— 它们的共同点是：都需要在几何绘制完成后， 以屏幕空间为定义域，重新访问场景表面。

技术家族消费 G-Buffer 的什么代表实现

屏幕探针式 GIDepth + Normal 放置探针；BaseColor / Roughness 做最终合成UE5 Lumen
按需分配的阴影Depth 决定需要哪些阴影页Virtual Shadow Maps

反过来读这张表：放弃 G-Buffer，就同时放弃了上面这一整列。 你放弃的不是「一种光照调度方式」，而是整个屏幕空间技术栈。 在 UE5 里这条推论尤其锋利 —— Lumen、Nanite、Virtual Shadow Maps 全部只在延迟路径上受支持。

05

四个原理级硬约束

Hard limits · 不是实现缺陷，是架构的必然

MSAA 悖论

硬件 MSAA 的做法是「每像素多个覆盖采样点，共享一次着色，最后平均」。 延迟渲染要 MSAA，G-Buffer 就得变成 multisampled，显存与带宽 ×4/×8。 但真正致命的不是成本，而是你不能先 resolve G-Buffer 再打光。看下面这个像素。

悖论的一句话形式 MSAA 平均的必须是 BRDF 的输出（颜色，线性可加），而 resolve G-Buffer 平均的是 BRDF 的输入（材质参数，非线性）。 前向渲染天然平均前者，所以 MSAA 免费；延迟渲染只能平均后者，除非 per-sample 打光 —— 成本 ×N。 业界折中是「边缘检测 + stencil 标记，只在边缘 per-sample」，复杂度极高。 主流引擎的延迟路径干脆不提供 MSAA，改用时域方案（TAA / TSR）。

半透明：一个像素放不下两层表面

G-Buffer 每个像素只能存一组表面属性，而半透明的定义就是「一个像素上叠了多层表面」。 玻璃后面还有玻璃，玻璃后面还有墙。

这在原理上无解。理论上可以用 A-Buffer、每像素链表、Deep G-Buffer 保存多层， 但存储是不定长的 —— 成本与复杂度都不可接受。

所以半透明必须走前向。这不是某个引擎的实现选择， 而是任何延迟渲染器都必须做的让步 —— 也正因如此，第 06 节的「混合管线」不是可选项，是唯一形态。

材质表达被固定布局锁死

想加一种新的着色模型？你得去抢着色模型 ID 的 bit、抢自定义数据的通道。 想让一个材质「两层法线各自算光照」？G-Buffer 只有一份法线槽位。 每加一种材质能力，就要再占一整张全屏渲染目标的带宽。

业界的解法方向是用变长的材质字节流替代固定通道布局： 材质声明任意分层结构，序列化成变长数据，光照 Pass 反序列化后逐层求解 —— 着色模型的枚举上限和通道争抢在这个模型下都不再存在。 UE5 的 Substrate 是这个方向的一个实现，5.8 中仍默认关闭。

带宽：唯一随分辨率平方增长的那一项

回到 FIG 03 的数字。1080p 下 G-Buffer 一帧写约 79 MB，4K 直接 ×4 到 316 MB， 而光照、AO、反射、GI、贴花每一个 Pass 都要把它再读一遍。

在移动端的 TBDR GPU 上，这意味着 tile memory 装不下、必须回写系统内存 —— 带宽与功耗双爆炸。 但这一条有解，见 6.3。

06

混合才是常态

Not either/or · 这一节是理解的关键

最大的误解 很多教程讲到这里就结束了，把它讲成「二选一」。真实情况是：
真实引擎的每一帧，都是延迟与前向的混合产物。
UE5 是一个直接的证据：引擎里根本没有独立的前向场景渲染器类， 前向着色只是延迟渲染器内部的一个分支，两者共享可见性判定、共享阴影系统、共享光源剔除网格、共享后处理链。

一帧的结构

切换开关，观察帧结构如何塌缩。消失的那一大段橙色，就是整个屏幕空间技术栈。

混合点一 · 半透明永远走前向

即使项目是标准的延迟渲染，所有半透明材质都走独立的前向 Pass： 在不透明光照完成后，按从远到近排序，读取已渲染好的 SceneColor 作为背景， 在像素着色器里当场算完自己的光照，再混合上去。原因就是 5.2。

这里有一个漂亮的循环依赖：前向的半透明反过来消费了延迟管线的输出 —— 玻璃的屏幕空间折射，采样的正是延迟渲染刚刚算完的不透明场景颜色。它们不是竞争者，是分工者。

代价：半透明没有 Depth Prepass 保护，overdraw 会直接叠加。 多层玻璃、密集粒子、大面积透明特效是所有引擎共同的性能陷阱。 这也是为什么引擎通常为半透明提供一档「低精度体积光照」的近似方案 —— 烟雾粒子的光照之所以看起来「糊」， 就是因为它取自一张低分辨率的 3D 辐照度纹理，而不是逐像素计算。

混合点二 · 光源剔除网格是正交的基础设施

2.2 那张 froxel 网格常被当成「前向渲染的特征」。这是不准确的。

分簇光源剔除解决的是「哪些灯影响这个空间区域」， 这个问题与「几何属性在哪里汇合」完全正交 —— 所以两条管线都在用它。

在 UE5 里这一点可以被源码直接证实：延迟渲染器每帧无条件构建这份所谓的「前向」光照网格， 然后由半透明光照、体积雾、体积云、水体、头发、屏幕探针 GI、虚拟阴影贴图共同消费。 它是一份共享的空间索引，不属于任何一条管线。

混合点三 · TBDR 让延迟的带宽劣势消失

移动 GPU 是 TBDR 架构（Tile-Based Deferred Rendering），片上有一块极快的 tile memory。 如果把 G-Buffer 声明为「无内存后备」的临时附件， 并把几何 Pass 与光照 Pass 合并成同一个 render pass 的两个 subpass， 那么 G-Buffer 写入后可以直接在片上被读取，全程不回写系统内存。

再延迟一层：Visibility Buffer

【Pass 3】 常规延迟光照

这是把延迟思想再推一层：先延迟光照（G-Buffer），再延迟材质（Visibility Buffer）。 好处是几何光栅化与材质求值彻底解耦 —— 微多边形场景（每个三角形 ≈ 1 像素）不会因为 quad overdraw 而崩溃。

代价是它和 G-Buffer 绑死了：Visibility Buffer 管线无法在前向渲染下工作。 UE5 的 Nanite 是这个思路的代表实现，这也正是 Nanite 与前向路径互斥的根本原因。

选型

Decision · 三个问题，按顺序问

08

五句话

If you remember nothing else

  1. 唯一的分歧是「几何属性与光照信息在哪里汇合」 —— 前向在着色器寄存器里，延迟在显存（G-Buffer）里。所有其他差异都是这一个选择的推论。
  2. 延迟渲染真正的价值不是「支持很多光源」（Forward+ 也能做到）， 而是它产出了一张全屏场景描述，从而让整个屏幕空间技术栈 —— AO、反射、屏幕探针 GI、按需阴影、延迟贴花、时域重投影 —— 成为可能。
  3. 前向渲染真正的价值是 MSAA 和低带宽 —— 这两件事在原理上是延迟渲染做不到的，也正是 VR 与移动端的核心诉求。
  4. 不存在纯粹的延迟渲染：不透明走延迟，半透明必然走前向； 光源剔除网格两条管线共用；TBDR 上用 subpass 把延迟塞进片上内存，就能拿到前向的带宽特性。 它们是同一个渲染器里协作的两套子系统。
  5. 先问需求，再问性能：需要屏幕空间技术栈就只能延迟；需要 MSAA 或极低带宽就只能前向。 两者都能满足时，「哪个更快」必须实测 —— 它取决于分辨率、overdraw、光源覆盖率和 GPU 架构，没有先验答案。
收束 把延迟渲染记成：先把屏幕上可见的不透明表面压缩成一套材质数据库，再让光源查询这个数据库并累加光照。
把前向渲染记成：绘制表面的当下，取得该区域相关的灯光，把材质、光照、反射一次算完，直接输出颜色。
