# 前向渲染 vs 延迟渲染：一份因果链笔记

> 目标不是记住一张优缺点表，而是建立一个**能用来分析新问题**的心智模型。
> 全篇的组织原则：每个结论都标明它从哪个前提推导而来；条件变了，结论就该变。

---

## 0. 一句话核心

**前向渲染（Forward Rendering）**：以物体为外层循环，在片元着色器里当场把材质和所有光源算完 —— 着色发生在"这个片元最终是否可见"确定之前。

**延迟渲染（Deferred Rendering）**：先跑一遍几何，把**每个像素上深度测试胜出的那个表面**的材质参数固化到屏幕空间缓冲（G-Buffer），再以像素为单位统一做光照 —— 着色发生在可见性确定之后。

**类比**：
- 前向 = 每来一个客人，厨师从头做一份完整套餐；客人临走前可能被前面的人挡住看不见（浪费整份）。
- 延迟 = 先让所有客人排队报出"我要什么食材"，登记在一张座位表上（G-Buffer），确定谁真的坐下之后，再按座位统一上菜。登记表只有一行/座位，所以**一个座位坐不下两个人**（透明失效），登记表的字段是印好的（材质自由度受限）。

---

## 1. 核心分歧：一句话 + 逐词拆解

> **前向把光照循环嵌套在几何循环内部，代价是"片元数 × 光源数"；延迟先把可见表面的材质参数固化到屏幕空间，把代价重新参数化为"片元数 + 像素数 × 光源数"—— 本质是让光照代价与几何复杂度解耦。**

| 关键词 | 含义 | 为什么关键 |
|---|---|---|
| **嵌套** | `for 物体 { for 片元 { for 光源 } }` | 嵌套 = 乘法。乘法是所有前向性能问题的根源 |
| **可见性未确定** | 光栅化产生片元时，还不知道深度测试的最终胜者 | 决定了前向的"无效着色"从哪来 |
| **固化** | 把"这个表面是什么"从对象域搬到像素域 | G-Buffer 的本质定义，也是所有延迟代价的唯一来源 |
| **屏幕空间** | 存储的自变量从"物体"变成"像素" | 显存/带宽开销为什么与分辨率强相关 |
| **重新参数化** | 乘法项的自变量从"物体"换成"像素" | 像素数有上限（分辨率），物体数没有 —— 这就是延迟的全部收益 |
| **解耦** | 加物体不增加光照成本，加光源不增加几何成本 | 唯一真正的优势陈述 |

**一句话记住代价的来源**：延迟渲染的**所有**缺点，都是"每像素只能固化一个表面 + 固化用的字段是编译期定死的 + 固化要写读全屏缓冲"这三件事的直接推论。不是实现不当，是结构性后果。

## 2. 前置：管线里其实在做四件事

任何实时渲染都在解四个子问题。前向和延迟的区别，就是**这四件事的执行顺序和执行域不同**。

```
几何阶段        可见性判定        材质求值           光照计算
(顶点变换)  →  (深度测试/剔除) →  (采样贴图、       →  (对每盏光算 BRDF、
                                  算出 albedo/          阴影、衰减，累加)
                                  normal/roughness)
```

- **几何阶段**：把顶点从模型空间变到裁剪空间，产出三角形供光栅化。代价 ∝ 顶点数/三角形数。
- **可见性判定**：视锥剔除、遮挡剔除（CPU/GPU 粗粒度）+ 深度测试（逐片元细粒度）。决定"谁最终出现在这个像素上"。
- **材质求值**：跑材质图/着色器，采样贴图，得到表面参数（基础色、法线、粗糙度、金属度……）。
- **光照计算**：对每盏影响该表面的光源，求 BRDF、阴影、衰减，累加成最终颜色。

### 为什么"一个物体受多个光源影响"会重复计算

对同一个片元，材质求值只需要做一次，但光照必须对每盏光做一次。如果没有任何剔除机制，一个片元要跑 L 次 BRDF —— 其中大多数光源可能远在天边、衰减到零。**乘法关系 + 无效项占比高**，这就是要优化的对象。

关键量：**L̄ = 每片元平均"真正有贡献"的光源数**。它通常远小于场景总光源数 L。后面所有现代方案，本质都在做同一件事：**把 L 压到 L̄**。

## 3. 机制：两段伪代码 + 复杂度

### 符号约定

| 符号 | 含义 |
|---|---|
| `N` | 提交的 draw call / 物体数 |
| `V` | 顶点/三角形总量 |
| `P` | 屏幕可见像素数（1080p ≈ 2.07M，4K ≈ 8.29M）|
| `k` | overdraw 系数（光栅化产生的片元 ÷ 最终可见像素），典型 2~4 |
| `F` | 片元总数 = `P × k` |
| `L` | 场景光源总数 |
| `L̄` | 每片元平均有效光源数 |

### 前向渲染

```
// 变体 A：single-pass（所有光源塞进一个 shader 的循环）
for each object in N:
    vertex_shading()
    rasterize()
    for each fragment F_i:               // 可见性尚未裁决
        surface = evaluate_material()    // 采样贴图、算法线
        color = 0
        for each light in L:             // ← 嵌套在最内层
            color += BRDF(surface, light)
        depth_test_and_write(color)      // ← 可能在这里被整个丢弃

// 变体 B：multi-pass（每盏光重画一遍几何，加法混合）
for each light in L:
    for each object in N:
        ... 完整重画 ...
```

**复杂度**
- 顶点：`O(V)`（variant B 是 `O(V × L)` ← 这是灾难，也是"前向不能处理多光源"这个误解的来源）
- 片元：`O(F × L)` = `O(P × k × L)`
- **两种浪费**：① 被深度测试丢弃的片元上的完整着色（∝ `k-1`）；② 无贡献光源上的 BRDF（∝ `L - L̄`）

### 延迟渲染

```
// Pass 1: Geometry Pass —— 只回答"每个像素上是谁"
for each object in N:
    rasterize()
    for each fragment F_i:
        surface = evaluate_material()
        if depth_test_pass:
            write_gbuffer(surface)       // 写 20~40 字节，不做任何光照
// 此刻：可见性已完全裁决，G-Buffer 里每像素恰好一个表面

// Pass 2: Lighting Pass —— 循环主体换成了光源/像素
for each light in L:
    for each pixel covered by light_volume:
        surface = read_gbuffer(pixel)    // ← 每盏光都要读一次
        scene_color += BRDF(surface, light)
```

**复杂度**
- 几何 pass：`O(V)` + `O(F)` 材质求值与 G-Buffer 写
- 光照 pass（经典逐光源版）：ALU `O(P × L̄)`，**G-Buffer 读带宽 `O(P × L̄)`** ← 注意带宽项也乘了 L̄
- 光照 pass（Tiled/Clustered 版）：ALU `O(P × L̄)`，**带宽 `O(P)`** ← 带宽项的 L̄ 消失了

### 本质对照

| | 前向 | 延迟 |
|---|---|---|
| 循环嵌套 | `物体 → 片元 → 光源` | `物体 → 片元` **然后** `光源 → 像素` |
| 光照成本自变量 | 片元数 `F`（无上限） | 像素数 `P`（有上限 = 分辨率） |
| 着色 vs 可见性 | 着色在先 | 可见性在先 |

> **关键洞察**：延迟的收益不是"更快"，而是**把一个乘法项的自变量换成了有上限的量**。所以：光源越多、几何越复杂、overdraw 越严重，延迟赢面越大；反之全部反转。

## 4. 同一像素的对照推演

**场景**：100 个物体、10 个动态光源。取屏幕上某个像素：它被 3 个物体的片元覆盖（`k=3`），最终显示最前面那一个表面，该表面实际受 4 盏光影响（`L̄=4`）。

**理论最优**（不可能低于此）：1 次材质求值 + 4 次 BRDF。

| 方案 | 材质求值次数 | BRDF 次数 | G-Buffer 读写 | 浪费在哪 |
|---|---|---|---|---|
| 前向 naive | 3 | 3 × 10 = **30** | — | 不可见片元 ×2 + 无效光源 ×6/片元 |
| 前向 + 逐物体光源列表 | 3 | 3 × ~5 = 15 | — | 不可见片元；剔除粒度太粗（大物体横跨多光源区）|
| 前向 + Z-prepass | 1（+1 次纯深度）| 1 × 10 = 10 | — | 无效光源 ×6；几何提交两次 |
| **Forward+ / Clustered** | 1（+prepass）| 1 × 4 = **4** | — | 几乎无浪费 ✅ |
| 延迟（经典逐光源）| 3 | 4 | 写 ×3，**读 ×4** | 材质求值 ×2；G-Buffer 反复读 |
| **Tiled/Clustered Deferred** | 3 | 4 | 写 ×3，**读 ×1** | 只剩材质求值 ×2 ✅ |

### 从这张表能读出的因果

1. **哪些计算与物体数有关**：顶点处理、draw call、剔除。两条路径相同。
2. **哪些与光源数有关**：BRDF。前向乘的是"片元数"，延迟乘的是"像素数"。
3. **哪些发生在不可见表面上**：前向是**整套光照**被浪费；延迟只浪费**材质求值 + G-Buffer 写**。→ 这不是"延迟没有 overdraw"，是**延迟把 overdraw 的单位成本降低了**。
4. **为什么延迟能拆开材质和光照**：因为 G-Buffer 定义了一个**中间契约** —— 光照 pass 不需要知道这个表面来自哪个物体、用了哪张贴图、材质图有多复杂，它只需要 `(位置, 法线, albedo, roughness, metallic)`。**几何/材质的复杂度被这层契约完全隔离在光照之外**。这就是解耦的技术含义。
5. **最重要的一行**：Forward+ 那一行的数字（1 次材质 + 4 次 BRDF）**比延迟更优**，而且不付 G-Buffer 带宽。这就是为什么"前向 vs 延迟二选一"的框架在今天已经过时。

## 5. G-Buffer：延迟保存的表面信息

**正确的心智模型**：G-Buffer 不是"几张贴图"，而是**一份用屏幕像素为索引的、可见表面的参数快照**。它是几何/材质世界与光照世界之间的**接口定义**。选择 G-Buffer 布局 = 选择这个接口能表达什么。

### 典型通道构成（以 UE5 布局为参照）

| Buffer | 内容 | 格式 | 为什么必须存 |
|---|---|---|---|
| Depth/Stencil | 深度 + 模板 | D32S8 (8B) | 深度测试本来就需要；且它是**重建世界坐标的唯一依据** |
| GBufferA | World Normal (+ per-object 数据) | RGB10A2 (4B) | BRDF 的核心输入，且**无法从任何其他通道推导** |
| GBufferB | Metallic / Specular / Roughness / **ShadingModelID** | RGBA8 (4B) | BRDF 的形状参数；ID 决定光照 pass 走哪个分支 |
| GBufferC | Base Color (+ AO / 间接光) | RGBA8 sRGB (4B) | 反照率，能量分配的基础 |
| GBufferD | Custom Data（语义随 ShadingModelID 变）| RGBA8 (4B) | 非标准材质的额外参数（次表面颜色、清漆强度等）|
| GBufferE | 预计算阴影因子 | RGBA8 (4B) | 静态光照的烘焙结果 |
| Velocity | 屏幕空间运动矢量 | RG16F (4B) | TAA/TSR/运动模糊的前置依赖 |

> 具体通道数与打包方式**随引擎和版本变化**（UE5 还有各向异性通道、Substrate 路径下布局完全不同）。以你手上版本的 `BufferVisualization` 和文档为准。

### 为什么不直接存世界坐标

因为**它可以推导**：`世界坐标 = InverseViewProj × (屏幕UV, 深度)`。而深度本来就必须存（Z-test 需要）。存 `float32×3` 位置要多花 12 B/px，还有精度问题（远处大数值浮点精度差，而深度可以做非线性分布把精度集中在近处）。

> **这是 G-Buffer 设计的通用原则：只存不可推导的量。** 每一个通道都要过这一关。法线不能推导（必须存）；世界坐标能推导（不存）；视线方向能从像素坐标算出（不存）。

### 光照 pass 如何重建光照

```
像素坐标 + 深度  →  世界坐标 P
相机位置 - P     →  视线方向 V
GBufferA         →  法线 N
GBufferB/C/D     →  BRDF 参数（按 ShadingModelID 分派）
光源数据         →  光方向 L、颜色、衰减、阴影
                 ↓
            BRDF(N, V, L, params) × 阴影 × 衰减  →  累加进 SceneColor
```

注意这个 pass **完全不知道场景里有几个物体**。它只面对一张"表面参数图"。这就是解耦的具象体现。

### 带宽与显存开销（量级估算）

按上表约 **28 B/px**（5×RGBA8 + depth + velocity，实际布局有出入）：

| 分辨率 | 常驻显存 | 写入/帧 | 写入 @60fps | 经典逐光源读（L̄≈3）@60fps | 合计 |
|---|---|---|---|---|---|
| 1080p (2.07M px) | ~58 MB | 58 MB | ~3.5 GB/s | ~10 GB/s | **~14 GB/s** |
| 4K (8.29M px) | ~232 MB | 232 MB | ~14 GB/s | ~42 GB/s | **~56 GB/s** |

对照硬件带宽预算：

- **桌面独显**：中端约 450 GB/s，高端约 1 TB/s → 4K 下 G-Buffer 占总带宽的几个百分点到 10%。可观，但可以承受，尤其在 Tiled Deferred 消掉 `×L̄` 的读之后（4K 降到 ~28 GB/s）。
- **移动 SoC**：LPDDR5 系统内存约 50 GB/s，且被 CPU、GPU、显示控制器**共享**，还直接换算成功耗与发热。→ 即使 1080p 的 14 GB/s 也要吃掉近 1/4 的总预算。

> **这就是"移动端不走传统延迟"的定量理由** —— 不是延迟"不好"，是它把成本压在移动平台最稀缺的资源上。同一个方案在两种硬件上得出相反结论，正是"结论随条件变化"的典型例子。

### 格式选择为什么牵一发动全身

- **精度**：法线用 RGB8 会在大面积平滑表面上产生带状伪影 → 通常要 RGB10A2 或八面体编码。粗糙度精度不足会让高光呈阶梯状。
- **性能**：每多 4 B/px，1080p60 就多约 0.5 GB/s 的写带宽，4K60 多约 2 GB/s。**通道数是直接的性能旋钮。**
- **可扩展性**：布局在**编译期固定**。想加一种新材质参数，要么抢占已有通道（和别的材质冲突），要么加一整张全屏 RT（全场景付带宽）。→ 这条直接导出下一节的"材质多样性受限"。

## 6. 代价的结构性来源

四条短板，全部从**同一个前提**推导而来。这是本文最重要的一节。

### 前提回顾
- **(P1)** 每像素只能固化**一个**表面（深度测试选出唯一胜者）
- **(P2)** 固化的字段是**编译期定死**的固定布局
- **(P3)** 固化需要**写入并读回全屏缓冲**

### ① 透明物体 ← 来自 (P1)

半透明需要在同一像素上**按顺序累积多个表面**的贡献。G-Buffer 每像素只有一个槽位，深度测试的语义是"留下最近的、丢掉其余的"。**存不下 = 结构性不兼容**，不是引擎偷懒。

> 解法只有两类：(a) 透明物体走独立的前向 pass（几乎所有引擎的做法，包括 UE）；(b) OIT / 逐像素链表 / 加权混合 —— 用可变长度存储换正确性，带宽和复杂度都很高。
> **正确说法不是"延迟不能画透明"，而是"延迟路径下的透明必须由另一条路径承担"。**

### ② MSAA ← 来自 (P1) + (P3)

MSAA 之所以便宜，前提是 **"几何覆盖多采样、着色只做一次"**。延迟把着色搬到了屏幕空间的独立 pass 里，而那时"哪个 sample 属于哪个表面"的信息只存在于 MSAA 的 G-Buffer 中：

- 若先 resolve 再着色 → **错的**。平均后的法线/albedo 不对应任何真实表面（半法线 + 混合材质 = 物理上不存在的表面），边缘会出现明显错误。
- 若保留 MSAA G-Buffer 并 per-sample 着色 → **正确但昂贵**。显存和带宽 ×N，且着色也接近 ×N（可用 stencil 只对边缘像素做 per-sample 来缓解，但复杂度和不确定性大增）。

→ **MSAA "省钱的前提"被延迟的结构直接摧毁了。** 这就是为什么延迟渲染时代的抗锯齿全面转向后处理型（FXAA/SMAA）与时域型（TAA/TSR）。这个转向不是审美选择，是结构倒逼。

### ③ 材质多样性受限 ← 来自 (P2)

所有材质必须能被**同一组固定字段**描述。头发的各向异性、皮肤的次表面散射、布料的边缘散射、清漆的双层高光 —— 它们需要的参数和 BRDF 形式都不同。

**UE 的解法：ShadingModel ID。** 在 GBufferB 里存几个 bit 的整数，光照 pass 读到后 `switch` 到对应的 BRDF 实现，同时把 GBufferD（Custom Data）**重新解释**为该模型需要的参数。

> 这是一个很巧妙的设计，但要看清它的代价边界：
> - 它换来了"多种材质模型"，但**没有换来"任意材质"** —— 每加一个模型都要占 ID 空间、复用 Custom Data 通道、给光照 shader 加一个分支。
> - 分支在 GPU 上按 wave/warp 执行：同一 wave 内混着多种 ShadingModel 时会走**发散路径**，代价接近所有分支之和。材质模型在屏幕上越碎片化，损失越大。
> - UE5 的 **Substrate**（材质表达重构，按需分层/可变编码）正是在解这个结构性问题。它在 UE5 各版本中的成熟度差异较大，**务必核对你所用版本的文档**。

### ④ 带宽压力 ← 来自 (P3)

见上一节的数字。要点是它**与场景复杂度无关、与分辨率强相关** —— 空场景和满场景付一样的钱。这也意味着：**在简单场景 + 少光源下，延迟是纯亏损**（付了固定成本，没换到任何收益）。

## 7. 全维度对比

同一组维度、同一把尺子：

| 维度 | 前向（经典）| 延迟（经典）| 判据 / 为什么 |
|---|---|---|---|
| 光源数扩展性 | 差：`O(F × L)` | 好：`O(P × L̄)` | 乘法项的自变量不同 |
| 几何复杂度扩展性 | 光照成本随 overdraw 恶化 | 光照成本与几何无关 | G-Buffer 契约隔离了几何 |
| 带宽 | 低（无 G-Buffer） | 高且固定 ∝ 分辨率 | (P3) |
| 显存占用 | 低 | 1080p ~58 MB / 4K ~232 MB | (P3) |
| 透明处理 | 天然支持（顺序正确即可）| 必须另开前向 pass | (P1) |
| 抗锯齿 | MSAA 可用 | MSAA 结构性昂贵，实践上转 TAA/TSR | (P1)+(P3) |
| 材质自由度 | 高：每个 shader 可任意 | 受 G-Buffer 布局约束 | (P2) |
| Overdraw 敏感度 | 极高（浪费整套光照）| 较低（只浪费材质求值+写）| 着色在可见性之前/之后 |
| Early-Z 收益 | 大（但需 prepass 或好的排序）| 几何 pass 里同样受益 | 两者都吃这口饭 |
| 后处理友好度 | 需额外 pass 产出深度/法线 | G-Buffer 已经现成 | SSAO/SSR/DOF 天然需要这些 |
| 移动端 / TBDR | ✅ 首选 | ❌ 除非 G-Buffer 不落显存 | 带宽是移动端最贵资源 |
| 桌面端 / 高光源密度 | 需升级到 Forward+ | ✅ 舒适区 | 带宽预算充足 |
| VR | ✅ 常选（MSAA + 低延迟）| 分辨率高 → 带宽×2 眼，TAA 易鬼影 | 见第 9 节 |

> **不要把这张表当结论背下来。** 每一行右侧的"判据"才是可迁移的东西；表的左右两栏只是判据在特定参数下的取值。

## 8. 八个常见误解的纠正

| 说法 | 错在哪 | 什么条件下部分成立 | 正确说法 |
|---|---|---|---|
| ① "延迟一定比前向快" | 把"某个乘法项变小"当成"总成本变小"。忽略了 G-Buffer 的固定带宽成本 | 光源多、overdraw 重、几何复杂时 | 延迟用**固定的带宽成本**换**光照与几何解耦**。只有当解耦的收益超过这笔固定支出时才更快 |
| ② "前向无法处理大量光源" | 混淆了**朴素前向**和**前向这条路径**。这个印象来自 multi-pass 实现（`O(V×L)`）| 无任何光源剔除的朴素实现 | 加上 tile/cluster 剔除后（Forward+），前向能轻松跑上千光源，且每片元只遍历 `L̄` 盏 |
| ③ "延迟不会发生 Overdraw" | 几何 pass 照样光栅化、照样有被覆盖的片元 | 指的是"光照不会重复"时 | Overdraw 依然存在，但**被浪费的单位成本**从"材质+全部光照"降到了"材质+G-Buffer 写" |
| ④ "延迟不能渲染透明物体" | 混淆"这条 pass 做不到"和"这个渲染器做不到" | 指纯粹的 G-Buffer pass 时 | 延迟路径下的透明由**独立的前向 pass** 承担。所有实用引擎都是混合的 |
| ⑤ "前向画物体时一定为所有光源计算光照" | 只对最朴素的实现成立 | 无任何剔除时 | 逐物体光源列表、tile 剔除、cluster 剔除都能把 `L` 压到 `L̄` |
| ⑥ "用了 G-Buffer 就是传统延迟" | G-Buffer 是一种数据结构，不是一种架构 | 传统 Deferred Shading 确实用它 | Deferred Lighting、Visibility Buffer、Forward 的 depth+normal prepass 都产出类 G-Buffer 数据但架构不同。**看光照发生在哪、以什么为循环主体** |
| ⑦ "Forward+ 只是普通前向" | 忽略了它引入了一个**独立的剔除阶段**（compute shader 建 tile/cluster 光源列表）| 它确实保留了前向的循环嵌套 | Forward+ = 前向的循环结构 + 延迟式的屏幕空间光源剔除。是两条路线的**杂交**，不是前向的小改 |
| ⑧ "延迟的核心优势是减少 Draw Call" | 完全不相关。延迟的几何 pass 提交的 draw call 和前向**一样多**（甚至因为要单独跑透明 pass 而更多）| —— | 核心优势是**每个可见像素只被着色一次**，且光照代价与几何解耦。Draw Call 数量由批处理/Instancing/Nanite 决定，与渲染路径正交 |

## 9. 演进：为什么"二选一"的框架已经过时

把所有方案放到同一条脉络上：**每个方案都在回答"如何把 L 压到 L̄，同时少付固化的代价"。**

```
                            朴素前向  O(F × L)
                                 │
                 ┌───────────────┴────────────────┐
        保留循环结构，                        反转循环结构，
        加屏幕空间光源剔除                    先固化再着色
                 │                                │
          Forward+ / Tiled Forward         Deferred Shading
          O(F × L̄)，带宽低                 O(P × L̄)，带宽高
                 │                                │
          Clustered Forward              Tiled / Clustered Deferred
          （深度方向也切片，               （每 tile 只读一次 G-Buffer，
            透明也能查光源列表）             带宽项的 ×L̄ 消失）
                 │                                │
                 └───────────────┬────────────────┘
                                 │
                    Visibility Buffer（把材质求值也延迟）
                                 │
                          Hybrid（今天所有引擎的实际形态）
```

| 方案 | 关键改动 | 解决了什么 | 新增了什么成本 |
|---|---|---|---|
| **Forward+ / Tiled Forward** | Depth prepass + compute 建每 tile 光源列表；BasePass 只遍历本 tile 的光源 | `L → L̄`，同时**保住** MSAA、透明、材质自由度 | 几何提交两次；剔除的 compute 开销；tile 内深度跨度大时剔除失效 |
| **Clustered Forward** | Tile 在深度方向也切片（通常指数分布），形成 3D cluster | 修复 tiled 在深度跨度大时的剔除失效；**cluster 与深度缓冲无关，所以透明物体也能查同一套光源列表** | cluster 网格的构建与存储 |
| **Tiled / Clustered Deferred** | 光照 pass 从"每光源一个全屏 pass"改成"每 tile 读一次 G-Buffer、循环 tile 内光源" | **G-Buffer 读带宽从 `O(P×L̄)` 降到 `O(P)`** —— 延迟带宽问题的主要解药 | compute 路径的实现复杂度；tile 内材质分支发散 |
| **Deferred Lighting / Light Pre-Pass** | 瘦 G-Buffer（只存 depth+normal+高光参数）→ 算出光照累积缓冲 → **重新提交几何**，前向式地把 albedo 与光照合成 | 更小的 G-Buffer、更高的材质自由度 | 几何提交两次。在 PS3/360 那代带宽极紧时流行，今天少见 |
| **Visibility Buffer** | G-Buffer 里**不存材质参数**，只存 `(instance ID, triangle ID)` + depth（约 8 B/px）。着色时按材质分组，反查顶点数据、重建属性、才执行材质图 | 几何 pass 写带宽降到极低；**材质多样性完全恢复**（材质代码在着色时才跑）；对小三角形/高几何密度尤其有利 | 着色时要手动重建重心坐标与**属性导数**（无法用硬件插值和自动 mip 选择）；需按材质分类的间接调度 |
| **Hybrid** | 不透明走延迟/VisBuffer，透明走 Clustered Forward，毛发/皮肤走特化 pass，体积雾走 froxel | —— | 这不是妥协，是**承认不同子问题有不同的最优结构** |

> **Visibility Buffer 是"决策反转"的第二次推进**：第一次延迟了光照，第二次连材质求值也延迟了。这条脉络的方向很清楚 —— **持续把计算往"可见性已确定之后"推**。UE5 的 Nanite 走的正是这条路（Nanite 输出 visibility buffer，再由 material pass 解析成 G-Buffer）。

## 10. 落到 UE5

> 以下描述 **UE5** 的行为，不要与 UE4 混淆。UE5 各小版本变化不小（尤其 Substrate、Mobile Deferred、Nanite 兼容性），**请以你所用版本的官方文档和实测为准**。

### 路径分布

| 平台/场景 | 默认路径 | 设置项 |
|---|---|---|
| 桌面/主机 | **Deferred** | 默认，`DeferredShadingSceneRenderer` |
| 桌面 Forward | Clustered Forward（不是朴素前向）| Project Settings → Rendering → **Forward Shading**（`r.ForwardShading=1`），需重启并全量重编译着色器 |
| 移动端默认 | Mobile Forward（clustered）| `r.Mobile.ShadingPath=0` |
| 移动端延迟 | Mobile Deferred | `r.Mobile.ShadingPath=1`，依赖 Vulkan/framebuffer fetch 等设备能力；**成熟度随版本变化大，务必核对文档** |

### 最实际的一条结论：**在 UE 里选渲染路径，本质上是在选功能集**

| 功能 | 依赖路径 | 为什么 |
|---|---|---|
| **Nanite** | Deferred（与 Forward 不兼容/受限）| 输出 visibility buffer 再解析成 G-Buffer，整条链路建立在延迟结构上 |
| **Lumen** | Deferred | 需要 G-Buffer 与屏幕空间探针来做屏幕空间追踪与光照重建 |
| **Virtual Shadow Maps** | Deferred（Forward 下受限）| 依赖深度与延迟式的阴影投影/剔除机制 |
| **Substrate** | Deferred（重构 G-Buffer 表达）| 就是在替换固定 ShadingModel 布局这件事本身 |
| **MSAA** | **仅 Forward** | 见第 6 节 ②：延迟下结构性昂贵，UE 直接不提供 |
| **TSR / TAA** | Deferred 友好（需 velocity buffer + 历史帧）| 与 MSAA 互斥 |

> 所以"开了 Forward 之后画面变了、某些效果没了"**不是材质写错了**，是你换了一整套可用功能。这是使用 UE5 时最容易踩、也最该内化的一条。

### 为什么 UE 桌面默认延迟

"夜晚城市、100 盏动态点光源"：前向 naive 下每个片元要遍历 100 盏光，乘上 overdraw，成本失控；延迟下光照成本变成 `O(P × L̄)`，而 `L̄` 在光源体积剔除后可能只有个位数 —— 加光源近乎免费。加上 Lumen/Nanite/VSM 全部构建在延迟结构上，这个默认选择在桌面端是自洽的。

### VR 为什么常开 Forward + MSAA

三条独立理由叠加：
1. **带宽**：VR 是双眼高分辨率，G-Buffer 的固定成本几乎翻倍；
2. **抗锯齿质量**：VR 里几何边缘的锯齿在头动时极其刺眼，MSAA 的时序稳定性优于 TAA；
3. **TAA 的鬼影/模糊**在头显里被放大得很难忍受，且时域累积与低延迟需求冲突。

### 编辑器动手验证（建议按顺序做）

1. **看 G-Buffer**：Viewport → `Lit` 下拉 → **Buffer Visualization** → 逐个看 Base Color / World Normal / Roughness / Metallic / Scene Depth。把第 5 节的表对照着看一遍，"G-Buffer 是表面参数快照"这句话会从抽象变具体。
2. **看成本分布**：`ProfileGPU`（Ctrl+Shift+,）或 `stat gpu`。记下 BasePass 与 Lights 各自的耗时。
3. **验证解耦**：复制光源到 100 盏，重跑 ProfileGPU。→ **Lights 涨、BasePass 基本不动**。这就是 `O(P × L̄)` 的直接观测。再复制一堆几何，→ BasePass 涨、Lights 基本不动。**这一步做完，第 3 节的复杂度表就不再是背下来的了。**
4. **验证路径=功能集**：开启 Forward Shading 重启后，看 Anti-Aliasing Method 里 MSAA 是否出现；再回头看 Buffer Visualization 的 G-Buffer 通道是否还有有效内容；观察 Lumen/Nanite 的状态变化。
5. **看 Overdraw**：`viewmode shadercomplexity` 与 Quad Overdraw 视图，理解第 4 节里 `k` 这个系数在你的场景里到底是多少。
6. **移动端**：切到 Mobile Preview，对比 `r.Mobile.ShadingPath` 两种取值下的表现（注意版本差异）。

### 源码阅读顺序（可选深入）

`Engine/Source/Runtime/Renderer/Private/` 下：

1. `SceneRendering.cpp` / `DeferredShadingRenderer.cpp` —— 整帧的调度骨架，先建立全局地图
2. `BasePassRendering.{h,cpp}` —— 两条路径在这里分叉（延迟写 G-Buffer / 前向直接着色）
3. `ShaderGenerationUtil.cpp` + `Shaders/Private/DeferredShadingCommon.ush` —— G-Buffer 的实际编解码，看 ShadingModelID 怎么打包
4. `LightRendering.cpp` / `Shaders/Private/DeferredLightPixelShaders.usf` —— 光照 pass 与 ShadingModel 分派
5. `TranslucentRendering.cpp` —— 透明为什么必须单独走一条路

## 11. 选择框架

**不要从"选前向还是延迟"开始。** 按下面的顺序过一遍判据，答案通常会自己浮现，而且往往是"混合"。

### 第一步：先看有没有硬约束（这些直接定生死）

| 条件 | 结论 | 依据 |
|---|---|---|
| 必须用 MSAA（VR、CAD、高对比边缘）| → Forward | MSAA 与延迟结构性冲突 |
| 目标是移动端且无法用 subpass/framebuffer fetch | → Forward | G-Buffer 带宽超出移动端预算 |
| 必须用 Nanite/Lumen/VSM（UE5）| → Deferred | 功能集绑定 |
| 画面主体是半透明（粒子风、玻璃场景）| → Forward 为主 | 每像素单表面的限制 |

### 第二步：没有硬约束时，量化两个关键数

- **`L̄`（每像素平均有效光源数）**，不是场景总光源数。
  - `L̄ ≤ 2`：延迟的解耦优势几乎为零，但固定带宽成本全额支付 → **前向净胜**
  - `L̄` 上到十几、几十：延迟/Tiled Deferred 明显占优
  - 中间地带：Clustered Forward 通常两头都不亏
- **`k`（overdraw 系数）**：从 Quad Overdraw 视图实测。`k` 大 → 前向浪费整套光照，延迟只浪费材质求值 → 延迟优势放大。

### 第三步：其余因素作为修正项

| 因素 | 往哪偏 | 为什么 |
|---|---|---|
| 材质模型种类多（毛发/皮肤/布料/清漆）| 偏前向，或延迟 + 特化 pass | G-Buffer 布局固定 (P2) |
| 后处理重（SSAO/SSR/DOF/运动模糊）| 偏延迟 | 深度/法线/velocity 已现成，否则要额外 prepass |
| 4K/8K 或超采样 | 偏前向 | 延迟成本 ∝ 像素数，且是固定支出 |
| 显存紧张 | 偏前向 | 4K G-Buffer 就 ~232 MB |
| 场景几何极复杂、三角形极小 | 偏 Visibility Buffer / Nanite | 传统 G-Buffer 的写带宽和 quad overdraw 都在恶化 |
| 团队规模小、要用现成引擎默认 | 用引擎默认路径 | 逆着引擎的默认走，隐性成本很高 |

### 第四步：默认答案

> **不透明走延迟（或 Nanite→VisBuffer），透明走 Clustered Forward，特殊材质走特化 pass。**
> 这不是骑墙，是承认不同子问题的最优结构不同。今天几乎所有商业引擎都是这个形态。

## 12. 自测

### A. 五个核心问题（能区分"真懂"和"记住结论"）

**1. 为什么"延迟让每个可见像素只着色一次"在有 overdraw 的场景里仍然成立？它的前提是什么？**
> 前提：光照 pass 在深度测试完全裁决**之后**、在屏幕空间执行，此时每像素只剩一个胜出表面。G-Buffer 的**写入**仍然有 overdraw —— 被浪费的是"材质求值 + 写 20~40 B"，不是整套光照。所以准确说法是"**光照**只做一次"，不是"没有浪费"。

**2. 一个场景只有 1 盏方向光，但有 5000 个物体、几十种材质，选哪条？**
> **前向。** 延迟的收益（光照与几何解耦）在 `L=1` 时**几乎为零**，而代价（G-Buffer 写带宽、材质受限、显存）**全额支付**。此时延迟是净亏损。这题考的是：能不能说清"优势来自哪个量"，而不是条件反射地选延迟。

**3. Tiled Deferred 比经典逐光源 Deferred 快，省的具体是哪部分？**
> 省的是 **G-Buffer 的重复读带宽**（从 `O(P × L̄)` 次全屏读降到 `O(P)` 一次），**不是 BRDF 的算术量**（那部分基本不变，甚至因 tile 剔除更精确而略减）。这题考的是能不能分清 **bandwidth-bound** 与 **ALU-bound** —— 这是分析真实性能问题时最关键的一刀。

**4. MSAA 与延迟的冲突为什么是结构性的，而不是"把 G-Buffer 开成 MSAA 就行"？**
> MSAA 省钱的前提是"覆盖多采样、**着色单次**"。延迟把着色搬到了屏幕空间的独立 pass。若先 resolve 再着色，平均后的法线/albedo 不对应任何真实表面（结果是错的）；若保留 MSAA G-Buffer 并 per-sample 着色，则显存、带宽、着色全部近似 ×N —— **省钱的前提消失了**，只剩成本。所以不是"开个开关"的问题。

**5. Visibility Buffer 相对传统 G-Buffer，把什么又往后推了一步？收益和新成本各是什么？**
> 把**材质求值**也延迟了。收益：几何 pass 写带宽降到约 8 B/px；材质多样性完全恢复（材质代码在着色时才执行，不受固定布局约束）；对小三角形/高几何密度场景优势明显。新成本：着色时要反查顶点/索引缓冲、手动重建重心坐标与**属性导数**（失去硬件插值和自动 mip 选择），并需要按材质分类的间接调度。

### B. 三个易混场景判断题

**a. 移动端开延迟是不是一定更慢？**
> 不一定。若用 Vulkan subpass / framebuffer fetch / pixel local storage，让 G-Buffer **只在 tile memory 中流转、不落外部显存**，带宽代价基本可以消掉。结论取决于 API、驱动、设备支持，以及 G-Buffer 是否足够瘦、pass 中间是否需要邻域访问。无条件说"移动端永远别用延迟"是错的。

**b. 场景有 200 盏光源，但每盏半径都很小、物体分布稀疏 —— 延迟一定赢吗？**
> 不一定。Clustered Forward 也能把每片元的光源数压到个位数；此时前向因为**省掉 G-Buffer 的固定带宽**可能反而更快，还顺带保住 MSAA 和材质自由度。**真正的判据是 `L̄`（每像素平均有效光源数），不是场景总光源数 `L`。** 把 `L` 当判据是最常见的误判。

**c. 在 UE5 里开了 Forward Shading 之后，Lumen 效果没了、Nanite 网格表现异常 —— 是材质写错了吗？**
> 不是。是**功能集变了**：Lumen、Nanite、VSM 都构建在延迟路径的 G-Buffer 结构上。"在 UE 里选渲染路径 = 选功能集"这句话在这里直接兑现。

### C. 输出练习

用你自己的话，向一个只懂"顶点着色器/片元着色器/深度测试"的同事讲清楚这三件事，**每件不超过三句话，不许用"更快""更先进"这类词**：

1. 延迟渲染反转了哪个循环的嵌套顺序，为什么这个反转有意义；
2. G-Buffer 存不下透明物体，这件事是从哪个前提推出来的；
3. 为什么 Forward+ 出现之后，"前向 vs 延迟"就不再是一道二选一的题。

> 检验标准：如果你在讲第 2 条时用了"因为引擎不支持"，说明还停在结论层；正确的推导是"深度测试的语义是留下唯一胜者 → 每像素一个槽位 → 半透明需要多个表面 → 存不下"。

### D. 200 字记忆版

> 前向：物体外层、光源内层，着色发生在可见性裁决之前，成本 ∝ 片元数 × 光源数。延迟：先把可见表面的材质参数固化进屏幕空间 G-Buffer，再按像素统一光照，成本拆成 O(片元) + O(像素 × 光源)。**核心是用一次屏幕空间的"参数固化"，换取光照与几何复杂度的解耦。** 代价全部来自这次固化：每像素只能存一个表面（透明失效）、参数平均后无意义（MSAA 失效）、字段布局编译期固定（材质受限）、要写读全屏缓冲（带宽 ∝ 分辨率）。现代方案沿两条线消解代价：给前向加光源剔除（Forward+/Clustered），给延迟加分块着色（Tiled/Clustered Deferred），或把延迟推到极致只存三角形 ID（Visibility Buffer）。判据是每像素有效光源数与 overdraw，不是场景总光源数。

```
共同要解决的四件事：几何 → 可见性 → 材质 → 光照

前向：  几何 → 材质 → 光照 → 可见性        成本 O(F × L)
延迟：  几何 → 材质 → 可见性 ‖ 光照         成本 O(F) + O(P × L̄)
                          ↑
                    G-Buffer 在这里切开

延迟的三个前提 → 四个代价：
  每像素一个表面   → 透明失效
  参数平均无意义   → MSAA 失效
  布局编译期固定   → 材质受限
  写读全屏缓冲     → 带宽 ∝ 分辨率

所有现代方案在做同一件事：把 L 压到 L̄
```
