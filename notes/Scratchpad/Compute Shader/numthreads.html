1. 本质：两层结构

一句话：[numthreads(X, Y, Z)] 声明一个线程组（Thread Group）里有多少个线程，共 X×Y×Z 个。 它不决定你总共跑多少线程，只决定"一组"有多大。总量由 CPU 端的 Dispatch 决定。

GPU 执行 Compute Shader 是两层嵌套的。理解这一点，numthreads 就通了：

  • 外层（CPU 端）：Dispatch(gx, gy, gz) —— 我要发多少个组。
  • 内层（Shader 端）：[numthreads(X, Y, Z)] —— 每个组里有多少线程。
总线程数 = (gx × gy × gz) × (X × Y × Z)

这两个值是配对使用的。要处理一张 512×512 的图、每个像素一个线程，如果 numthreads 是 8×8×1， 那 Dispatch 就得发 512/8 = 64 × 64 × 1 个组。这个除法在 UE 里由 FComputeShaderUtils::GetGroupCount() 完成（向上取整）。

顺带把术语对齐一下，读 NVIDIA 文档时这两套词是混着用的：

层级HLSL / D3D / UE 叫法CUDA / NVIDIA 叫法
整次派发DispatchGrid（网格）
一组线程Thread Group（线程组）Block / CTA
硬件调度单位Wave（32 或 64）Warp（固定 32）
单个线程ThreadThread / Lane
组内共享内存groupshared / TGSM__shared__ / Shared Memory
最常见的错误就是 Dispatch 和 numthreads 对不上：shader 里写 numthreads(32,32,1)， C++ 里却按 8 去算组数 —— 要么少算（图像只处理了一部分），要么多发 4 倍的组（白白浪费）。 第 9 节有本项目里的真实例子。

3. 四种线程 ID

Shader 入口函数通过语义（Semantic）拿到"我是谁"。四个都常用，含义完全不同：

语义类型含义典型用途
SV_DispatchThreadIDuint3全局唯一坐标（跨所有组）当像素 / 数组下标用，最常用
SV_GroupIDuint3我属于第几个组分块（Tile）处理
SV_GroupThreadIDuint3我在组内的三维坐标索引 groupshared 数组
SV_GroupIndexuint组内坐标压平成一维（0 … X·Y·Z−1）一维遍历共享内存、归约；它决定线程属于哪个 warp

它们之间是纯粹的算术关系，numthreads 就是那个换算比例：

DispatchThreadID = GroupID × numthreads + GroupThreadID
GroupIndex = GroupThreadID.z×(X×Y) + GroupThreadID.y×X + GroupThreadID.x

注意第二个公式的形状：X 是变化最快的维度，Z 最慢。这不只是个约定 —— 下一节会看到， 它直接决定了哪 32 个线程被打包进同一个 warp，进而决定内存访问是否合并。上面的交互点一下格子， 这两个公式会用真实数字展开给你看。

三条铁律（这是 numthreads 所有选值建议的根源）：
  1. 一个线程组只会跑在一个 SM 上，且从开始到结束不迁移。 这就是为什么组内能有共享内存和同步（大家在同一块片上 SRAM 旁边）， 而跨组永远无法通信（可能在芯片两端的不同 SM 上，甚至根本没同时运行）。
  2. 一个组的线程数一旦超过硬件对单个 SM 的容量，就无法启动。 这就是 X×Y×Z ≤ 1024 这条限制的物理来源。
  3. SM 上可以同时驻留多个组（各自占一份寄存器和共享内存）。 驻留得越多，越能靠切换 warp 来掩盖内存延迟 —— 这就是 Occupancy，见第 6 节。

5. Warp：真正的执行单位

你写的是"一个线程做什么"，但硬件从不单独调度一个线程。 GPU 把组内线程按 SV_GroupIndex 顺序每 32 个打包成一个 Warp， 一个 warp 的 32 个线程共用一个指令指针，永远锁步执行同一条指令（SIMT）。

由此推出三个非常实际的结论：

① 组内线程数应该是 32 的倍数

不足 32 的部分会补齐成一整个 warp，多出来的 lane 被屏蔽掉空转，但依然占着调度槽位和寄存器。 numthreads(8,1,1) = 8 个线程 = 仍然占用 1 个完整 warp，算力利用率只有 8/32 = 25%。

AMD 的 wave 是 64（RDNA 可切 32）。取 64 的倍数能同时让两家都对齐，是最稳妥的选择。

② X 维度决定了 warp 的形状

因为 GroupIndex 里 X 变化最快，numthreads(32,2,1) 的 warp 0 是"第 0 行的 32 个线程"（一条横线）， 而 numthreads(8,8,1) 的 warp 0 是"前 4 行 × 8 列"（一个 8×4 的方块）。

这直接影响内存合并（Coalescing）：warp 内 32 个线程如果访问的是连续地址，硬件可以合并成极少的几次事务； 如果散乱，就退化成多次访问。读写线性 Buffer 时长条形更好；采样 2D 纹理时方块形更好（贴合纹理的 swizzle 缓存布局）。 UE 默认 8×8 就是为后者优化的。

③ 分支发散（Divergence）在 warp 内才有代价

// 坏：同一个 warp 内的 32 个线程会分裂成两条路，硬件只能串行跑完两边 → 耗时翻倍
if (DTid.x % 2 == 0) { HeavyA(); } else { HeavyB(); }

// 好：以 warp 为粒度分叉，整个 warp 走同一条路 → 无代价
if (GroupIndex < 32) { HeavyA(); } else { HeavyB(); }

跨 warp 的分支不算发散。所以"能不能把条件对齐到 32 的边界"是优化 Compute Shader 的常用手段。

7. groupshared 与片上内存

如果只是"每个像素一个线程"，为什么还要分组？因为同一组内的线程能协作，跨组的不能。 回到第 4 节的铁律一：一个组固定在一个 SM 上，所以它们能共用那块 128 KB 的片上 SRAM。

  • 共享内存：groupshared 变量存在 SM 内部，延迟约 20~30 周期， 而访问显存（VRAM）要 400~800 周期。差了一个数量级还多 —— 这就是分块（Tiling）算法的全部意义。
  • 同步：GroupMemoryBarrierWithGroupSync() 让组内所有 warp 在此对齐。跨组没有任何同步手段。
// 经典模式：先协作加载到共享内存，同步，再计算（模糊、卷积、归约都这样写）
groupshared float4 Tile[8][8];

[numthreads(8, 8, 1)]
void MainCS(uint3 DTid : SV_DispatchThreadID, uint3 GTid : SV_GroupThreadID)
{
    Tile[GTid.y][GTid.x] = InputTexture[DTid.xy];   // 1. 每人从显存搬一块（慢，但只做一次）
    GroupMemoryBarrierWithGroupSync();               // 2. 等组内所有 warp 都搬完
    // 3. 现在可以高速读邻居搬来的数据了
    float4 Sum = Tile[GTid.y][GTid.x] + Tile[GTid.y][(GTid.x + 1) % 8];
    OutputTexture[DTid.xy] = Sum * 0.5;
}
两个注意点
① groupshared 数组尺寸必须和 numthreads 手动保持一致，编译器不检查逻辑关系。 HLSL 下每组上限通常是 32 KB（D3D11 TGSM 限制），远小于硬件的 128 KB —— 硬件那 128 KB 是给 多个同时驻留的组分的。
② Bank Conflict：NVIDIA 的共享内存分成 32 个 bank（正好对应 warp 的 32 条 lane）。 如果同一 warp 内多个线程访问了同一个 bank 的不同地址，访问会被串行化。 典型症状是 Tile[GTid.x][GTid.y] 这种列优先访问 —— 常见解法是把数组宽度 +1 做 padding （Tile[8][9]）把访问错开。

8. 怎么选 numthreads

硬性规则（违反直接编译失败）

  • X × Y × Z ≤ 1024。
  • Z ≤ 64。
  • 必须是编译期常量 —— 不能是运行时变量，所以 UE 用宏注入（见第 9 节）。

性能规则（能跑，但会慢）

  • 取 64 的倍数：对齐 NVIDIA 的 warp32 和 AMD 的 wave64，尾部不空转。
  • 别太小：(8,1,1) 这种，一个 warp 里 24 条 lane 白白空转，同时组数量暴增撞上"每 SM 最多 N 个组"的上限。
  • 别太大：1024 线程的组占用大量寄存器和共享内存，一个 SM 塞不下第二个组， 延迟掩藏能力骤降（见交互二）。而且组越大，末尾的边界浪费越多。
  • 形状要贴合访问模式：读线性 Buffer 用长条（X 大），采样 2D 纹理用方块，处理体数据用立方。

实用推荐

场景推荐值硬件层面的理由
2D 图像 / 后处理(8, 8, 1) = 64UE 默认；2 个 warp，方块形贴合纹理缓存
2D 大分辨率、追求占用率(16, 16, 1) = 2568 个 warp；各架构都能跑满 Occupancy
1D 数组 / 粒子 / 归约(64,1,1) 或 (256,1,1)长条形，warp 内地址连续，完美合并访存
3D 体数据 / 体积雾(4, 4, 4) = 64立方块贴合 3D 空间局部性
需要大块 groupshared降到 (8,8,1) 或更小共享内存是稀缺资源，组越大越挤不下

不确定就用 (8,8,1)。UE 把 8 定义成了 FComputeShaderUtils::kGolden2DGroupSize （"黄金" 2D 组大小），就是这个意思。真要调优，用 Nsight Graphics 看实测 Occupancy 和访存效率，别猜。

9. UE 中的写法（含本项目实例）

numthreads 必须是编译期常量，而组数在 C++ 里算 —— 为了不让两处数字失配， UE 的标准做法是：在 C++ 里定义宏，通过 ModifyCompilationEnvironment 注入给 shader。

C++ 端

// Plugins/TestShader_V2/Source/TestShader_V2/Private/TestShader_V2_Core.cpp
#define NUM_THREADS_PER_GROUP_DIMENSION_X 32
#define NUM_THREADS_PER_GROUP_DIMENSION_Y 32
#define NUM_THREADS_PER_GROUP_DIMENSION_Z 1

static void ModifyCompilationEnvironment(const FGlobalShaderPermutationParameters& Parameters,
                                        FShaderCompilerEnvironment& OutEnvironment)
{
    FGlobalShader::ModifyCompilationEnvironment(Parameters, OutEnvironment);
    OutEnvironment.SetDefine(TEXT("THREADGROUPSIZE_X"), NUM_THREADS_PER_GROUP_DIMENSION_X);
    OutEnvironment.SetDefine(TEXT("THREADGROUPSIZE_Y"), NUM_THREADS_PER_GROUP_DIMENSION_Y);
    OutEnvironment.SetDefine(TEXT("THREADGROUPSIZE_Z"), NUM_THREADS_PER_GROUP_DIMENSION_Z);
}

USF 端

// Plugins/TestShader_V2/Shaders/Private/TestShader.usf
[numthreads(THREADGROUPSIZE_X, THREADGROUPSIZE_Y, THREADGROUPSIZE_Z)]
void MainComputeShader(uint3 DispatchThreadId : SV_DispatchThreadID,
                       uint GroupIndex : SV_GroupIndex)
{
    float2 p = DispatchThreadId.xy / 512.0;
    // ...
    RenderTarget[DispatchThreadId.xy] = float3(x, y, z);
}

Dispatch 端

// 把"要处理多少元素"换算成"要发多少组"，内部是向上取整的除法
auto GroupCount = FComputeShaderUtils::GetGroupCount(
        FIntVector(Params.X, Params.Y, Params.Z),   // 总工作量，如 512×512×1
        FComputeShaderUtils::kGolden2DGroupSize);   // 每组的边长 = 8

FComputeShaderUtils::Dispatch(RHICmdList, ComputeShader, *PassParameters, GroupCount);
本项目当前就存在第 1 节说的那个失配。USF 的 numthreads 是 32×32×1（=1024，正好顶到硬件上限）， 而 GetGroupCount 传的却是 kGolden2DGroupSize（= 8）。 512×512 会发 64×64 = 4096 个组，但每组覆盖 32×32 像素 —— 实际启动了 4 倍于需要的线程。 多出来的线程写到纹理范围外（被硬件丢弃，画面看着正常），但算力白烧了约 75%。

更糟的是：1024 线程的组本身就是个次优选择。按第 6 节的交互算， 一个 SM 只能驻留 1 个这样的组，Occupancy 天花板只有 66.7%。

推荐改法：把三个宏改成 8 / 8 / 1，与 kGolden2DGroupSize 自动一致， 两个问题一起解决。（另一种改法是把 GetGroupCount 第二个参数改成 FIntVector(32,32,1)， 但这只修好了失配，没修好组过大。）

10. 边界检查

组数是向上取整算出来的，所以当工作域尺寸不是 numthreads 的整数倍时（比如 50×50 配 8×8 → 7×7 组 = 56×56 线程）， 边缘会多出线程。在交互一里选 "50 × 50" 就能看到红色的越界区域。

  • 写 UAV / RWTexture：硬件自动丢弃越界写入，通常不会崩，但算力浪费。
  • 写 StructuredBuffer 或用 groupshared 做归约：越界数据会污染结果，必须手动挡住。
[numthreads(8, 8, 1)]
void MainCS(uint3 DTid : SV_DispatchThreadID)
{
    // 养成习惯：入口先做边界检查
    if (any(DTid.xy >= TextureSize)) return;
    // ... 安全了
}
陷阱：如果函数里有 GroupMemoryBarrierWithGroupSync()，就不能用 return 提前退出。 同步的硬件语义是"组内所有 warp 都到达此处"，提前退出的线程不参与同步 → 行为未定义甚至挂起。 这种情况要改成把越界线程的数据填成中性值（0 或单位元），让它们照常走完同步流程。

11. 一分钟速查

  • [numthreads(X,Y,Z)] = 一个组内的线程数，不是总数。总线程 = Dispatch 组数 × numthreads，两者必须配套。
  • 硬件映射：组 → 一个 SM（永不迁移）；32 线程 → 一个 Warp（真正的调度单位）；线程 → 一条 Lane。
  • 组能有共享内存和同步，正是因为它固定在一个 SM 上；跨组无法通信，同理。
  • 线程按 SV_GroupIndex（X 最快变化）每 32 个打包成 warp —— 这决定了访存合并与分支发散的代价。
  • X×Y×Z ≤ 1024、Z ≤ 64；实际取 64 的倍数；过大反而降低 Occupancy。
  • 2D 图像用 (8,8,1)，追占用率用 (16,16,1)；1D 用 (64,1,1)；3D 用 (4,4,4)。
  • 入口习惯性写边界检查，但有同步时不能提前 return。
