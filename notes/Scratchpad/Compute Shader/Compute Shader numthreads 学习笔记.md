# Compute Shader numthreads 学习笔记

> 围绕 `numthreads(x, y, z)` 取值影响的完整问答总结：从线程组形状的区别，一路追问到内存合并、sector/cache line、LSU 与 SM 硬件结构。

---

## 疑问一：`numthreads(8,8,1)` 和 `numthreads(32,2,1)` 有什么区别？

### 结论先行

两者的线程组**总大小相同**（都是 64 线程），所以在"量"的层面完全一样：

- 每组 warp 数相同（NVIDIA 上都是 2 个 warp）
- 占用率（occupancy）相同
- `GroupMemoryBarrierWithGroupSync()` 的同步范围相同
- groupshared 配额相同

真正的区别在于**形状**：64 个线程在三维空间如何排布，它决定了**线程 ID → 数据的映射关系**。

### 根本规则：线程按 x 优先线性化，再按顺序打进 warp

```
SV_GroupIndex = x + y * numX + z * numX * numY   // x 变化最快
```

GPU 按 GroupIndex 顺序，每 32 个线程划为一个 warp（AMD 为 32/64）：

- `(8,8,1)`：warp0 = GroupIndex 0~31 = **(x=0..7, y=0..3)，一块 8×4 的像素块**；warp1 = y=4..7
- `(32,2,1)`：warp0 = **(x=0..31, y=0)，完整的一行 32×1**；warp1 = 第二行

```
(8,8,1) 的一个线程组:              (32,2,1) 的一个线程组:
y=0  [ w0 w0 w0 w0 w0 w0 w0 w0 ]   y=0  [ w0 w0 w0 w0 ... w0 ]  (32个)
y=1  [ w0 w0 w0 w0 w0 w0 w0 w0 ]   y=1  [ w1 w1 w1 w1 ... w1 ]
y=2  [ w0 × 8 ]                    ← 一个 warp 是一整行
y=3  [ w0 × 8 ]
y=4..7 [ w1 × 8 ]                  ← 一个 warp 是 8×4 的块
```

### 形状带来的五方面影响

**1. 全局内存合并（coalescing）** —— 详见疑问二。

**2. 分支分化（divergence）**：warp 内分支不一致时两条路径串行执行。
- 分支条件依赖 **y**（如"图像上半做 A、下半做 B"）：`(32,2,1)` 每个 warp 只含一行 → warp 内分支一致；`(8,8,1)` 一个 warp 跨 4 行 → 可能分化。
- 分支依赖 **x** 则正好相反。

**3. subgroup / wave 内在函数的 lane 布局**：`WaveReadLaneAt`、quad 操作按线性 lane 编号工作。
- `(8,8,1)`：**lane+8 就是正下方的像素**（前 3/4 的行在同一 warp 内）→ 可用 shuffle 免 groupshared 取垂直邻居。
- `(32,2,1)`：垂直邻居在另一个 warp → shuffle 用不上。
- 一个 quad（lane 4k~4k+3）在两者中都是 1×4 水平条，而非 2×2 方块。

**4. groupshared tile 形状与 halo 冗余**：卷积、模糊、tile-based 光照要先读一块 tile 进 groupshared 并多读一圈边缘（halo）。tile 越方，周长/面积比越小：
- 8×8 tile：周长 32，面积 64
- 32×2 tile：周长 68，面积 64 —— 同样面积，冗余边缘多一倍多

**5. Dispatch 网格与边界浪费**：同样覆盖 1920×1080，总线程数一样，但 Dispatch 参数不同：
- `(8,8,1)` → `Dispatch(240, 135, 1)`
- `(32,2,1)` → `Dispatch(60, 540, 1)`

尺寸不能整除时，浪费集中在哪条边取决于 tile 形状。

### 经验法则

1. **先定总量**：取 warp 的整数倍，64~256 是常用甜区（上限 1024，z ≤ 64）。
2. **再按问题定形状**：
   - 2D 图像 + 邻域/stencil 算法 → 接近方形：`8×8`、`16×16`
   - 1D 缓冲、按行的算法、subgroup 行内归约 → 长条形：`x=32~256, y=z=1`
   - 3D 体数据 / 纹理数组切片 → 用上 z，如 `4×4×4`
3. 尽量让 warp 落在分支条件一致的维度上。
4. 对纯逐像素操作（无邻居通信、无分支），两种形状性能差距通常只有几个百分点——先写对，再靠 profile 决定。

## 疑问二：两种情况是不是"都派发了 4 次 32 条 lane"？`(4,8,1)` 是不是浪费了一半 lane？

### 需要掰开的两个概念：lane 的利用 ≠ sector 的利用

**一条 load 指令，32 条 lane 同时产生 32 个地址，只执行一次**——不存在"派发 4 次 lane"。之后由内存合并器（coalescer）把 32 个地址按 **32B sector**（DRAM/L2 的取数粒度）归类，产生若干次 sector 事务。

32 条 lane × 4B(float) = **128B 有用数据**，这在各种形状下都相同。

### 三种形状对账表（float、行主序图像、行宽足够大且 32B 对齐）

| numthreads | 一个 warp 的布局 | 有用字节 | 取回 sector 数 | 触及 128B cache line 数 | 最坏利用率 |
|---|---|---|---|---|---|
| (32,2,1) | 1 行 × 128B 连续 | 128B | 4（取回 128B） | 1 | 100% |
| (8,8,1) | 4 行 × 32B | 128B | 4（取回 128B） | 4 | 100% |
| (4,8,1) | 8 行 × 16B | 128B | 8（取回 256B） | 8 | 50% |
| (1,32,1) 极端 | 32 行 × 4B | 128B | 32（取回 1024B） | 32 | 12.5% |

### 关键结论

**1. (32,2,1) vs (8,8,1)：sector 数完全一样（都是 4 个），谁也不浪费字节。** 前者一个 warp 访问 32 个完全连续的地址；后者每 8 个地址连续成一段（32B），共 4 段，每段恰好填满一个 sector。真正的区别在 **cache line 数（1 vs 4）** → L1 流水线处理的趟数不同（详见疑问三），这就是"只差几个百分点"的来源。

**2. (4,8,1) 的"浪费一半"方向对，但机制不是 lane 闲置。** 32 条 lane 全在干正事，产出的 32 个地址都有用。浪费发生在**取数粒度**上：每行段只有 16B，但硬件最少取一个 32B sector，于是取回 256B、只用 128B。准确说法是 **sector 过取（over-fetch）50%**，而不是"16 条 lane 白跑"。

**3. 这 50% 是否变成真实 DRAM 浪费，取决于复用。** 每个 sector 的另外 16B 属于 x 方向相邻的线程组，相邻 group 调度时间接近，大概率通过 L2 命中被用掉 → 实际浪费可能很小；最坏情况（L2 在两次访问间把它踢掉，或访存模式本身离散无复用）才是实打实的带宽减半。

### 实用结论

让 warp 在 x 方向的连续覆盖 **≥ 一个 sector**（float 数据即 x ≥ 8，最好凑满 32）。这就是 8×8、16×16 成为默认选择，而 (4,8,1)、(1,32,1) 这类窄条形状要避开的根本原因。另外行宽（pitch）最好按 32B 对齐，否则连 (32,2,1) 也可能跨 sector 甚至跨 line。

## 疑问三：cache line 数怎么理解？sector 越多"执行次数"越多吗？体现在谁身上？

### 两个粒度的分工

- **sector（32B）= 取数粒度**：缓存 miss 时实际从 L2/DRAM 搬多少数据，按 sector 算。
- **cache line（128B = 4 个 sector）= 管理粒度**：L1 缓存以 128B 为一个管理单元，每条 line 有自己的 tag（标签）。判断地址在不在 L1 里，按 line 查 tag。

**cache line 数的算法**：把 32 个地址分别除以 128（`地址 / 128`），落在几个不同的 128B 对齐块里，就是几条 line。

### "执行次数"不在 shader 核心，而在内存流水线

一条 warp 的 load 指令，从 SM（流多处理器）的角度看**只发射一次**，32 条 lane 同时算地址。之后：

```
SM 发射 1 次 load
   ↓
合并器把 32 个地址按所属 cache line 分组 → M 条 line
   ↓
L1 流水线逐条 line 处理（查 tag、取数据）→ 走 M 趟（M 个 wavefront，约 M 个流水线周期）
   ↓
每条 line 里缺哪些 sector，就向 L2/DRAM 请求 → 搬回 N × 32B
```

"次数"体现在两个不同的地方，对应两种不同开销：

| 数量 | 体现在 | 开销性质 |
|---|---|---|
| cache line 数 M | L1/LSU 流水线处理 M 趟（tag 查找、数据回送） | **流水线周期**：这条指令多占内存管道几拍 |
| sector 数 N × 32B | L2↔L1、DRAM↔L2 之间实际搬运的字节数 | **带宽**：线上多跑了没用到的字节就是浪费 |

套回例子（一次 warp load，有用数据都是 128B）：

- `(32,2,1)`：1 条 line → L1 走 1 趟；4 个 sector → 搬 128B，全用上
- `(8,8,1)`：4 条 line → L1 走 4 趟；4 个 sector → 搬 128B，全用上。**带宽一样省，只是流水线多走 3 趟**
- `(4,8,1)`：8 条 line → L1 走 8 趟；8 个 sector → 搬 256B，只用一半。**流水线更贵，带宽还可能浪费一半**

> 验证工具：Nsight Compute 指标 `l1tex__data_pipe_lsu_wavefronts`（L1 走了几趟）、`l1tex__t_sectors_pipe_lsu_mem_global_op_ld`（取了多少 sector），指标名随架构版本略有差异。

## 疑问四：LSU、"L1 流水线"是什么？如何对应到 SM 硬件结构图？

（对照 Blackwell 一代的 Streaming Multiprocessor 结构图）

### 名词定位

- **LSU（Load/Store Unit，加载/存储单元）= 图中每个分区底部的 `LD/ST` 小块**（每分区 8 个，全 SM 共 32 个）。
- **"L1 流水线"不是图里的某一个框**，而是 load 指令从 LD/ST 发出后、在底部 **256 KB L1 Data Cache / Shared Memory** 内部处理的数据通路（NVIDIA 官方叫 L1TEX pipeline，Nsight 指标里的 `data_pipe_lsu` 就是它）。它按"每拍处理一条 128B cache line"的节奏工作，"走几趟"就是这个管道被占了几个周期。

### 一条 load 指令在 SM 图上的完整旅程（从上到下）

```
① Warp Scheduler（橙色，每分区 1 个）
   每拍挑一个 warp，发射一条指令。warp 的 32 条 lane 固定映射到
   本分区的 32 个 CUDA core。——"指令只发射一次"发生在这里
② Dispatch Unit（棕色）
   把指令派给对应执行单元：算术给 CUDA core，访存给 LD/ST
③ LD/ST（= LSU，每分区 8 个）
   算出 32 条 lane 的 32 个地址；合并器在这里把地址按 128B line 归组
④ 256 KB L1 Data Cache / Shared Memory（底部蓝色长条，4 个分区共用）
   内部流水线逐个 wavefront 处理：每拍处理一条 128B line
   （查 tag + 读写其中最多 4 个 sector）
   ——触及 M 条 line = 占这个管道 M 拍，这就是"L1 走 M 趟"
⑤ miss 时请求离开 SM → L2（在 SM 之外，不在 SM 图里）→ 再 miss 去显存
   数据按 32B sector 搬回 ——带宽浪费发生在这一段线上
⑥ 结果写回 Register File（每分区 16384×32-bit），指令完成
```

三个例子的差异就体现在第 ④ 步：(32,2,1) 占 1 拍、(8,8,1) 占 4 拍、(4,8,1) 占 8 拍。

### SM 图上容易混淆的几个点

- **顶部的 `L1/L0 Instruction Cache` 是指令缓存**，存 shader 机器码，和底部存数据的 L1 Data Cache 完全两码事。
- **底部的 256 KB 是 L1 数据缓存和 shared memory 共用的一块 SRAM**。HLSL 的 `groupshared` 就住在这里——用多了会挤压 L1 可用空间（carveout 可配置），也是影响 occupancy 的因素之一。
- **`Tex`（纹理单元）** 的采样请求也汇入同一条 L1TEX 通路，纹理访存同样受 line/sector 规律支配。
- SM 内部有 **4 个独立分区**，各自有 scheduler，每拍全 SM 最多发射 4 条不同 warp 的指令；但一个 warp 的 32 条 lane 永远在同一分区内锁步执行，不会跨分区。
- `SFU`（特殊函数）、Tensor Core / TMA / TMEM 与普通 load 路径无关。

### 一句话总结硬件链条

**调度器负责"发射一次"，LSU 负责"算地址并归组"，L1 流水线按 cache line 逐拍消化，sector 按 32B 在缓存层级间搬运。**

## 生活化类比：仓库拣货

> 你在仓库**下单一次**买了 **32 件货**（一条指令、32 条 lane）。
> 货分布在几个**货架**（128B cache line），**拣货员就要跑几趟**（wavefront，L1 流水线的拍数）；
> 而每件货只能按**整箱出库**（32B sector），你要 16B 也得搬一整箱，
> 箱子里**剩下的半箱就是过取的浪费**。

### 类比映射表

| 仓库 | GPU |
|---|---|
| 下单一次 | SM 发射一条 load 指令（只发射一次） |
| 32 件货 | 32 条 lane 各自要的一个数据 |
| 拣货员 / 分拣台 | LSU（LD/ST）+ 地址合并器 |
| 货架（一个货架一格管理） | 128B cache line（按 tag 管理） |
| 拣货员跑的趟数 | wavefront 数 = L1 流水线被占的拍数 |
| 整箱出库的最小单位 | 32B sector（取数粒度） |
| 只要 16B 也搬一整箱 | sector 过取（over-fetch） |
| 另外半箱被同事的订单用掉 | 相邻线程组经 L2 复用，浪费被掩盖 |
| 货从总仓运到门店 | L2 / 显存 → L1 的数据搬运（带宽消耗） |

三种形状用类比说：

- `(32,2,1)`：32 件货在**同一个货架**上且正好拼成 4 整箱 → 跑 1 趟，搬 4 箱，箱箱装满。
- `(8,8,1)`：32 件货分在 **4 个货架**，每个货架上正好 1 整箱 → 跑 4 趟，搬 4 箱，箱箱也装满（不浪费搬运，就是人多跑了几趟）。
- `(4,8,1)`：32 件货分在 **8 个货架**，每个货架只要半箱 → 跑 8 趟，搬 8 箱，每箱倒腾出来只用一半。

## 核心结论速查

### 关键硬件常数

| 概念 | 数值 | 意义 |
|---|---|---|
| warp（NVIDIA） | 32 lane | 锁步执行、分支分化、合并访存的基本单位 |
| wavefront（AMD） | 32 / 64 lane | 同上，GCN 为 64 |
| sector | 32B | 内存取数粒度（浪费按它算） |
| cache line | 128B = 4 sector | L1 管理粒度（流水线趟数按它算） |
| numthreads 总量 | ≤ 1024，z ≤ 64 | 常用 64~256，取 warp 整数倍 |

### 形状选择经验法则

1. 先定总量（64~256，warp 整数倍），再按数据维度定形状。
2. 2D 图像 / stencil → 方形（8×8、16×16），halo 冗余最小。
3. 1D / 按行算法 → 长条形（x=32~256）。
4. **warp 在 x 方向的连续覆盖 ≥ 一个 sector**（float 下 x ≥ 8，最好 32），避开 (4,8,1)、(1,32,1) 这类窄条形状。
5. 让 warp 落在分支条件一致的维度上。
6. 用到 wave/subgroup 内在函数时，记住 lane 按 x 优先线性排布。
7. 行宽（pitch）按 32B 对齐。
8. 纯逐像素操作对形状不敏感（差距通常仅几个百分点）——先写对，再 profile，用 Nsight Compute 的 wavefronts / sectors 指标验证。
