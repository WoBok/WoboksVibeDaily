一次 Dispatch 在 GPU 里的四次切分

从 Dispatch(64,64,1) 配 numthreads(8,8,1)，到执行单元上的一条 32 lane 指令，中间发生了四次切分。每一次切分对应一层硬件，也对应一类性能约束——理解调度，就是理解这四层的边界在哪、代价是什么。

概览整条路径

整条路径

Dispatch → SM → Warp → SMSP → Lane

下面这条链路是全文的骨架。左侧是每一层的工作单位，右侧是这一层实际发生的事。

注意有两个独立的参数在不同层生效：Dispatch 决定有多少个线程组，numthreads 决定每组有多少线程。两者互不影响，来源也不同——前者是 CPU 运行时传入的，后者编译时就写死在 shader 里。

切分 1Dispatch → 线程组

Dispatch 展开成线程组

4096 个互不相干的任务包

两个数字来自两个不同的地方，这是最容易混淆的一点：

[numthreads(8, 8, 1)]      // 编译时写死在 shader 字节码里
void CSMain(...) { }

ctx->Dispatch(64, 64, 1);  // 运行时由 CPU 传入

组的数量 = Dispatch 三参数相乘 = 4096。每组线程数 = numthreads 三参数相乘 = 64。两者都是纯软件概念，与 GPU 有多少 SM 无关——同一份代码在任何一张卡上都是 4096 组 × 64 线程，只是大卡能同时处理更多组。这正是 GPU 程序可移植的来源。

线程组是什么

同一个东西在各处的叫法：HLSL 的 thread group、CUDA 的 block、Vulkan 的 workgroup、NVIDIA 硬件文档里的 CTA。它的本质定义是「一批能互相协作的线程」，而协作只有两种形式：共享 groupshared 内存，以及用 barrier 互相等待。跨组做不到这两件事，所以这个边界才有意义。

为什么整组不可拆分

因为这两个特性逼着硬件必须为每个在飞的组维护一份状态：

  • groupshared 要求组内所有线程看到同一份数据 → 硬件要在某个 SM 的 L1/Shared 里划一块，并记住基址与长度
  • GroupMemoryBarrierWithGroupSync() 要知道这组共几个 warp、到了几个 → 需要一个计数器
  • 组内 warp 全部退出后才能释放上面两样 → 需要存活 warp 计数

这三份状态没法存在 warp 里（warp 之间不知道彼此存在），必须存在一个 per-block 的地方。这个「地方」就是下文的 block 槽位。

组与组之间则完全没有顺序保证：第 4000 组可能比第 3 组先跑完。这就是 compute shader 里无法跨组同步的硬件原因。

切分 2线程组 → Warp

组内按线性序切成 warp

行主序展平，每 32 个一刀

线程组进入 SM 后，按行主序展平成一维，再每 32 个切成一个 warp：

linearIdx = GTid.x + GTid.y * 8      // 即 SV_GroupIndex
warp 0  →  GTid.y = 0..3   (32 个线程)
warp 1  →  GTid.y = 4..7   (32 个线程)

不能整除时，最后一个 warp 会用无效 lane 补齐。numthreads(10,10,1) = 100 线程需要 4 个 warp，最后一个只有 4 条 lane 活跃，直接浪费 22% 的发射槽——线程组大小应当是 32 的倍数，这是最基本的一条。

warp 的形状决定访存效率

切分方式还有一个不那么直观的后果：8×8 布局下，一个 warp 覆盖的是 4 行 × 8 列，而不是一行 32 个。

同理，分支也应当尽量对齐 warp 边界。在 8×8 下，if (GTid.y < 4) 恰好按 warp 分界、零发散；而 if (GTid.x < 4) 会让每个 warp 内部一半 lane 走 A 路、一半走 B 路，两条路径串行执行。

切分 3Warp → 子分区

warp 绑定到子分区

一次绑定，终身不变

一个 SM 被切成 4 个子分区（SMSP），每个子分区有独立的 L0 指令缓存、Warp Scheduler、Dispatch Unit、寄存器堆、CUDA Cores、Tensor Core、LD/ST 和 SFU。L1 指令缓存、L1/Shared Memory、纹理单元则是整个 SM 共享的。

warp 被分派到某个子分区后永久绑定，这带来两个后果：

  • 它的寄存器静态占用该子分区的寄存器堆，直到整个 block 结束才释放
  • 它只能使用这一个子分区的执行单元，用不到隔壁的

64 线程的组会让 2 个子分区空闲吗

不会。工作分发器不是「发一个组、等它跑完再发下一个」，而是持续灌入直到撞上资源上限。SM 上同时驻留着几十个组，硬件按空闲槽位轮转分配，所以 block 0 的两个 warp 去 SMSP 0/1，block 1 的去 SMSP 2/3，block 2 又回到 0/1……四个分区都是满的。

真正会空闲的只有两种情况：Dispatch 的组数少于 GPU 的 SM 数量，以及整个 Dispatch 收尾时的拖尾阶段。

切分 4Warp → Lane

发射：32 这个数字从哪来

架构常数，不是核心数推导出来的

常见的误解是「因为一个子分区有 32 个 CUDA Core，所以 warp 是 32 线程」。因果关系是反的：warp = 32 线程是从 2006 年 G80 起就写死在 ISA 里的架构常数，NVIDIA 后来才把 FP32 数据通路做成 32 宽去匹配它。

历史上两者经常不相等。G80 每个分区只有 8 个 SP，warp 照样是 32，一条 FP32 指令要分 4 个时钟才发射完；Turing 每分区 16 个 FP32 单元，一条 FP32 指令占 2 个时钟。真正的规律是：

核心规律

一条指令永远作用于 32 条 lane。执行单元有几条，只决定这条指令要占用几个周期。

用同一个 SM 里的其他单元就能验证：

单元每子分区宽度一条 warp 指令耗时典型 HLSL 操作
CUDA Core321 周期FP32 / INT32 算术
LD/ST84 周期Buffer 与 groupshared 读写
SFU48 周期sin rsqrt exp

这解释了为什么超越函数比乘加慢一个数量级——不是延迟高，是吞吐窄。

Blackwell 在这一层有个变化：白皮书说明 GB20x 把 INT32 核心与 FP32 核心完全统一，许多整数指令吞吐相对 Ada 翻倍，但统一后的核心在任一时钟周期内只能作为 FP32 或 INT32 之一工作。

约束驻留与占用率

驻留：延迟掩盖能力的度量

同时摊开在一个 SM 上的 warp 数量

warp 从进驻 SM 那一刻起，它的寄存器和所属 block 的 groupshared 就被静态占住，中途不释放，直到整个 block 结束。

好处是切换 warp 零开销：不需要保存和恢复上下文，因为所有 warp 的寄存器本来就同时躺在寄存器堆里，调度器只是换一个索引去读。代价是寄存器堆有限，能同时摊开的 warp 数有硬上限。

这个数量直接等于延迟掩盖能力。一次显存访问要 400~600 个周期：驻留 1 个 warp 就只能干等，执行单元全程空转；驻留 32 个，就能在等待期间轮流执行另外 31 个。

四个约束，取最小值

一个 block 想进驻，必须同时拿到四样东西——block 表项、warp 槽位、寄存器、共享内存。任何一样不足就在队列里等。

把这条规则用起来只需要三步：算出每个约束各自允许多少组，取最小值，再乘以每组的 warp 数。占用率 = 得到的 warp 数 ÷ 硬件上限。

block 槽位到底是什么

就是前面那三份 per-block 状态（shared 基址、barrier 计数、存活 warp 数）的存放位置——SM 里一张固定行数的硬件表。行数在流片时定死，因为它是实打实的触发器面积。

关键性质是：一条表项的成本与组的大小无关。32 线程的组和 1024 线程的组各占一行。所以线程组过小时，会出现「block 表用光了，warp 槽位还空着一半」的浪费——这在 Ampere 消费级（16 条表项）上很常见，Blackwell 把表项提到 32 条后大幅缓解。

组太大也有代价

  • 粒度太粗：1024 线程 = 32 warp，一个 SM 只放得下 1~2 个组，Dispatch 收尾时拖尾明显
  • barrier 更贵：要等 32 个 warp 全部到齐，只要一个卡在慢速访存上，其余 31 个全部干等
  • 寄存器要一次凑齐：组是原子进驻的，拿不到全部资源就一个都进不来

实际甜点区通常是 128~256 线程（4~8 个 warp）。

反直觉但重要

占用率不是越高越好。如果 shader 是纯 ALU 密集、几乎不访存，就没有延迟需要掩盖，20% 的占用率也能跑满执行单元；此时给每线程多分配寄存器、减少重复计算反而更快。占用率是手段，只在被内存延迟卡住时才重要。

实践可直接执行的结论

调优检查清单

按收益从高到低

  • 线程组大小取 32 的倍数。否则最后一个 warp 会带着无效 lane 空跑，浪费是纯损失。
  • 先看 warp 形状，再看占用率。访存密集的 shader 里，把 8×8 改成 32×2 常常比提升占用率收益更大——两者线程数相同、占用率相同，但合并访存效率差一个数量级。
  • 组大小落在 128~256。太小浪费 block 表项，太大导致粒度粗、barrier 贵、拖尾严重。
  • 盯住寄存器用量。每线程 128 个寄存器时，256 线程的组只能驻留 2 个 = 16 warp，占用率掉到 33%。减少活跃变量生命周期、避免大的临时数组，比调组大小更有效。
  • 分支对齐 warp 边界。8×8 下 GTid.y < 4 零发散，GTid.x < 4 则两条路径全部串行。
  • 先确认自己是否被延迟卡住。纯 ALU 密集的 shader 提升占用率没有收益，用 Nsight Graphics 或 RGP 看实际瓶颈再动手。
