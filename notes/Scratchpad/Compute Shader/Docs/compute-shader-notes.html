01Dispatch × numthreads：两级如何配合完成一个任务

一句话：[numthreads(X, Y, Z)] 写在 shader 里（编译期固定），决定一个线程组（Thread Group，CUDA 叫 thread block）有多大； Dispatch(gx, gy, gz) 在 CPU 端调用（运行期决定），决定发射多少个组——注意参数是组数，不是线程数。
总线程数 = (gx·X) × (gy·Y) × (gz·Z)
两者配合完成一个任务的标准套路是四步：
  1. 定工作单元：一个线程干一份活，通常是"一个线程处理一个像素 / 一个数组元素"。
  2. 定总量：比如一张 1920×1080 的图。
  3. 定组大小：numthreads(8,8,1)，每组覆盖 8×8 像素。
  4. Dispatch = 总量 ÷ 组大小，向上取整，shader 里做边界检查：
// CPU 侧：组数必须向上取整（不能整除时最后一组会越界）
cmd->Dispatch((width + 7) / 8, (height + 7) / 8, 1);
[numthreads(8,8,1)]
void CS(uint3 dtid : SV_DispatchThreadID)
{
    if (dtid.x >= width || dtid.y >= height) return;  // 边界守卫，必须有
    // 处理像素 (dtid.x, dtid.y)
}

为什么 numthreads 是编译期常量、Dispatch 是运行时参数？因为编译器要在编译时就完成寄存器分配、groupshared 布局、warp 打包与屏障代码生成，这些都依赖组大小；而 Dispatch 每次调用传入，同一个 shader 不改代码就能处理任意尺寸的输入。所以实际项目里 Dispatch 参数几乎总是 (size + tile - 1) / tile 这种 ceil 除法。

硬性上限（D3D）：Dispatch 每维 ≤ 65535 组；numthreads 总量 X·Y·Z ≤ 1024 且 Z ≤ 64；groupshared 每组 ≤ 32 KB。

02四个线程 ID 是怎么算出来的

硬件真正"给"的只有两个，另外两个是纯算术推导：

ID类型来源 / 计算唯一性
SV_GroupIDuint3调度器分发线程组时写入：这是第几个组，范围 [0, gx)×[0, gy)×[0, gz)全局唯一（标识组）
SV_GroupThreadIDuint3线程在组内的三维坐标，范围 [0, X)×[0, Y)×[0, Z)组内唯一，跨组重复
SV_GroupIndexuint由 GroupThreadID 线性化：gi = x + y·X + z·X·Y（x 变化最快）组内唯一，跨组重复
SV_DispatchThreadIDuint3由前两个算出来：dtid = GroupID × (X,Y,Z) + GroupThreadID全局唯一（标识线程）
为什么 GroupIndex 最关键：它是四个 ID 里唯一的标量，而且它就是 warp 的打包顺序——GPU 按 GroupIndex 顺序每 32 个线程切一个 warp。所以 numthreads 的形状决定了一个 warp 覆盖数据的形状（见第 6 节）。

两个容易踩的坑：

  • 没有内置的"全局线性索引"，想要自己算：flat = dtid.y · (gx·X) + dtid.x（用 Dispatch 网格宽度，不是数据宽度）。同理也没有一维组编号：linearGID = gid.y · gx + gid.x，且 gx 要自己通过 constant buffer 传进去——shader 里读不到 Dispatch 的参数。
  • 越界 return 不会省算力：那些线程仍占着 warp 的 lane 和寄存器，只是被屏蔽不写结果。所以尺寸对齐到 numthreads 的倍数有真实收益。

04Group → SM → warp：调度与驻留

4.1 从 Dispatch 到 SM：谁在分发

调用 Dispatch 后，GPU 前端的 GigaThread Engine / Compute Work Distributor（CWD） 手里握着全部线程组，它只做一件事：不停地问每个 SM"还塞得下一整个组吗"，塞得下就放一个进去（整组 all-or-nothing）。有组执行完退出，CWD 立刻补位。

SM（Streaming Multiprocessor，流多处理器）是 GPU 的基本计算单元——Blackwell GB202 满配 192 个 SM，每个 SM 含 128 个 CUDA core，内部再分 4 个处理块（SMSP）。SM 内部每个模块的职责，推荐对照这个交互式架构图看： GB202 GPU 交互式架构图 ↗

三条必须内化的规则：
  • 组的执行顺序无保证——别写任何依赖"组 5 在组 3 之后执行"的代码。
  • 组之间不能同步——没有跨组 barrier；跨组协调只能拆成两次 Dispatch。千万别在 shader 里自旋等另一个组：会死锁（你等的组可能还没被分发，而你占的资源正是它需要的）。
  • 驻留后不迁移——组放进某个 SM 就待到全组退出，寄存器和 groupshared 整段独占。

4.2 warp 是什么，怎么划分

warp = 32 个线程锁步执行同一条指令（SIMT；HLSL 里叫 wave，CUDA 叫 warp——同一个东西）。它是 SM 内真正的最小调度单位。warp 里的一条线程位置叫 lane（0~31）。

组进入 SM 后按 GroupIndex 顺序切成 warp：warp 数 = ceil(线程数 / 32)。64 线程 = 2 个 warp；100 线程 = 4 个 warp（最后 28 条 lane 空转但仍占资源）——所以 组大小必须是 32 的倍数。

同一个组的所有 warp 必须落在同一个 SM 内，只能在该 SM 的 4 个 SMSP 之间分配，绝不跨 SM。这是两条硬约束决定的：

  • groupshared 是 SM 本地的物理 SRAM，同组线程要共享它就必须在同一块 SRAM 旁；
  • GroupMemoryBarrierWithGroupSync() 是 SM 内的硬件屏障电路，跨 SM 同步要慢几个数量级。

4.3 驻留 ≠ 发射：SMSP 到底在干什么

"一个 SMSP 处理一个 warp"的直觉只对了一半。真实图景：

  • 每个 SMSP 同时驻留最多 12 个 warp（CC 12.0：48 warp/SM ÷ 4 分区）；
  • 每时钟周期从这 12 个里挑 1 个 ready 的，发射它的 1 条指令；其余 11 个在等（等内存、等 barrier、等前序结果）；
  • 切换零开销：每个驻留 warp 的寄存器始终物理占用寄存器堆的一块，切换只是换个索引——GPU 用海量寄存器换来了免费的上下文切换。

一次显存访问要 400~800 个时钟周期。GPU 隐藏延迟的办法简单粗暴：让足够多的 warp 驻留，一个等内存就切下一个，调度器一刻不闲。这就是占用率（occupancy）的物理意义，也是下一节的主题。

05交互②：占用率 —— 什么限制了 warp 驻留

CWD 要把一个组放上某个 SM，必须同时满足四类资源，差一个都放不下，而且是整组 all-or-nothing。对，这就是占用率（Occupancy）问题：

Occupancy = 实际驻留 warp 数 / 硬件最大驻留 warp 数（CC 12.0 = 48）

两个反直觉的结论：

  • 1024 线程的组在 CC 12.0 上永远达不到满占用率：32 warp/组，48 不能被 32 整除，第二组塞不进去 → 上限 66.7%。常用甜区是 64~256。
  • 占用率不是越高越好：计算密集、ILP 高的 kernel 50% 占用率可能更快；但低于 25% 几乎肯定是寄存器或 groupshared 出了问题。寄存器数用 Nsight 的 "Registers Per Thread" 和 "Achieved Occupancy" 实测，别靠猜。

06交互③：内存合并 —— warp 形状如何决定访存效率

先厘清三个名词：

  • lane：warp 里的一个线程位置（0~31）。一条 load 指令，32 条 lane 同时产生 32 个地址，只发射一次。
  • sector（32 字节）：内存的取数粒度。你要 4 字节，硬件也至少搬一整个 32B sector。
  • cache line（128 字节 = 4 个 sector）：L1 缓存的管理粒度。一条 load 触及几条 line，L1 流水线就要处理几趟。

发射之后，内存合并器（coalescer）把 32 个地址按所属 sector 归组，落在几个 sector 就搬几个——这就是 Memory Coalescing（内存合并 / 合并访存）。32 个地址挤在越少的 sector 里，效率越高。

形状为什么重要：二维数据在内存里是一维的（行与行之间隔了整整一行宽）。warp 横向铺开 → 地址连成一片；纵向铺开 → 被行距撕开。而 warp 覆盖什么形状，正是由 numthreads 的形状决定的（warp 按 GroupIndex 打包，x 变化最快）。

把形状从 32×1 一路换到 1×32，你会看到：同样的 32 个线程、同样的数据、同样的索引公式，搬运量从 128B 涨到 1024B，效率从 100% 掉到 12.5%——唯一变的只有 warp 的形状。结论压成一条判据：

numthreads.x × 单元素字节数 ≥ 32（一个 sector） → 满效率；不达标按比例线性掉
  • (8,8,1) 处理 float/float4 完全没问题（8×4B = 32B 恰好填满一个 sector）；要避开的是 (4,8,1)、(1,32,1) 这类窄条形状，以及 half/R8 小元素配小 X。
  • sector 数决定带宽浪费，cache line 数决定 L1 流水线趟数——前者是线上多搬的字节，后者是这条指令多占内存管道的拍数，两种开销分开算。
  • 过取的字节若被相邻线程组经 L2 复用，实际浪费会被掩盖；最坏情况才是实打实的带宽损失。纹理（Texture2D）走 swizzle 布局，对 warp 形状不那么敏感。
  • 同理可解释分支发散：分支条件依赖 y 时用长条形状让整个 warp 落在同一行 → 零发散。
