一次 Dispatch 到底发生了什么

线程怎么被编号、怎么被切成 warp、怎么塞进 SM、什么在限制它们的驻留、以及 warp 的"形状"如何决定显存带宽的浪费程度。硬件参数以 NVIDIA Blackwell（GB202 / 计算能力 12.0）为准。

00 一条链路看全貌

整个 Compute Shader 的执行，是一条从"软件描述的任务规模"逐级降解到"硬件执行单元"的链路。后面每一节都是在拆解这条链路上的某一段。

一句话串起来：Dispatch 说"要多少组"，numthreads 说"每组多少人"，两者相乘得到总线程数；硬件把组整体丢到某个 SM 上，SM 再把组内线程按 SV_GroupIndex 每 32 个打包成一个 warp，warp 才是发射指令、访问显存的最小实体。

01 Dispatch × numthreads

这是两个不同层级的"尺寸"，分别写在两个不同的地方，编译期与运行期各管一半。

如何配合完成一个任务

典型任务：处理一张 W × H 的图，让一个线程负责一个像素。你先定组的形状（受硬件偏好约束），再反推需要多少组。

// ---------- Shader 端 ----------
RWTexture2D<float4> Output;
[numthreads(8, 8, 1)]              // 每组 64 线程 = 2 个 warp
void CSMain(uint3 tid : SV_DispatchThreadID)
{
    if (tid.x >= W || tid.y >= H) return;   // 边界丢弃
    Output[tid.xy] = Shade(tid.xy);
}

// ---------- CPU 端 ----------
// 向上取整，保证覆盖所有像素
Dispatch( (W + 7) / 8, (H + 7) / 8, 1 );
向上取整必然多发线程。 W=100 时 ceil(100/8)=13 组，实际覆盖 104 列，多出 4 列。所以 shader 里那句 if (tid.x >= W) return; 不是可选项。反过来，如果你能保证分辨率是组尺寸的整数倍，就可以省掉这个分支。
组与组之间没有任何顺序和同步保证。 它们可能在不同 SM 上并行、也可能排队串行执行。组内可以用 groupshared 内存和 GroupMemoryBarrierWithGroupSync() 协作；跨组想同步，只能拆成两次 Dispatch。这是因为"组"就是硬件的分发单位——一旦分发出去就各跑各的。

02 四个 SV 值是怎么来的

硬件在启动每个线程时，会把它在"组网格"和"组内"的坐标写进寄存器。四个 SV 值全部由这两个坐标推导，没有别的信息来源。

语义值类型含义 / 计算取值范围

SV_GroupThreadIDuint3硬件直接给：本线程在组内的坐标[0, X-1] × [0, Y-1] × [0, Z-1]
SV_DispatchThreadIDuint3GroupID · (X,Y,Z) + GroupThreadID

    uint3 gtid : SV_GroupThreadID,     // (3, 2, 0)
    uint3 dtid : SV_DispatchThreadID,  // (1*8+3, 0*8+2, 0) = (11, 2, 0)

{ ... }
SV_GroupIndex 是四个里唯一的标量，也是最重要的一个。 它就是硬件展平线程组的顺序，warp 的划分完全按它来：warp 号 = GroupIndex / 32，lane 号 = GroupIndex % 32。所以"X 维变化最快"这件事直接决定了同一个 warp 里的 32 个线程在二维上长什么形状 —— 这是第 05 节访存效率的根源。它同时也是 groupshared 数组最自然的索引。

回到上面的沙盘：把着色模式切到 按 SV_GroupIndex，你会看到每个组内部的颜色是逐行（沿 X）由深到浅递增的；切到 按 Warp，就能看到这个递增序列每 32 个被切一刀。

03 线程组 → SM → Warp

软件侧的"组"和"线程"到了硬件侧，会变成"驻留在 SM 上的资源占用"和"锁步执行的 32 条 lane"。

分发：整组不可拆分

Dispatch 提交后，GPU 前端的工作分发器把一个个线程组派给有空闲资源的 SM。关键规则：

  • 一个线程组完整地落在一个 SM 上，永远不会被拆到两个 SM。因为组内要共享 groupshared 内存、要能互相同步，而这些机制只在单个 SM 内部存在。
  • 一个 SM 可以同时容纳多个组（Blackwell 上限 24 个）。容纳多少取决于资源够不够 —— 这就是第 04 节的占用率。
  • 组一旦上了 SM 就不会被换出，占着资源直到整组执行完毕。GPU 没有线程上下文切换到显存的机制。
延伸
SM（Streaming Multiprocessor）的内部构成、GPC/TPC 层级、L1/L2 的位置等 GPU 架构细节，见 GB202 GPU 交互式架构图；官方参数见 NVIDIA RTX Blackwell GPU Architecture 白皮书。

Warp 是什么

Warp = 32 个 GroupIndex 连续的线程被硬件捆成一束，共用一套取指/译码/发射逻辑，一条指令同时喂给 32 条 lane。这就是 SIMT（Single Instruction, Multiple Threads）。

  • lane 是硬件通道，thread 是软件概念。一条 lane 在某个时刻执行某个 warp 的某个线程。二者一一对应但不是一回事 —— 说"32 条 lane 同时发出 32 个地址"是在描述硬件行为。
  • 分支发散（divergence）：warp 内的线程走了不同分支，硬件只能串行执行每条路径，用掩码屏蔽掉不该执行的 lane。两条路径的耗时相加。所以分支粒度最好对齐到 32 的倍数。
  • 尾巴浪费：线程组大小不是 32 的倍数时，最后一个 warp 有空闲 lane，但它依然占满一个完整的 warp 槽位。numthreads(10,10,1) = 100 线程 → 4 个 warp，最后一个只有 4 条 lane 有效。

驻留（Residency）：GPU 隐藏延迟的方式

warp 一旦被分配到 SM，它的寄存器就常驻在寄存器堆里不动。调度器每个周期从所有驻留 warp 里挑一个"就绪"的发射指令 —— 切换 warp 是零开销的，因为根本不需要保存/恢复上下文。

这就是 GPU 对付显存延迟（数百个周期）的全部秘密：当 warp A 卡在等数据时，调度器立刻发射 warp B、C、D……只要驻留的 warp 足够多，执行单元就不会闲着。驻留 warp 数量不足 = 延迟藏不住 = 性能掉。

04 占用率 Occupancy：谁在限制驻留

占用率 = SM 上实际驻留的 warp 数 ÷ SM 的最大 warp 槽位数。四种资源同时在卡这个数，取最紧的那个。

Blackwell GB202（计算能力 12.0）每 SM 的硬上限

资源上限 / SM说明
Warp 槽位48（= 1536 线程）4 个分区各 12 个槽位
Block 槽位24 个线程组能同时驻留的组数上限
寄存器堆65536 个 32-bit4 个分区各 16384 个；单线程最多 255 个
共享内存100 KB 可分配与 L1 共用 128 KB；D3D 单组 groupshared 上限 32 KB
"block" 就是"线程组"。 NVIDIA/CUDA 文档叫 thread block（简称 block），D3D/HLSL 叫 thread group，Vulkan/GL 叫 work group —— 同一个东西的三个名字。所以"block 槽位"= 一个 SM 能同时装下的线程组个数。

计算规则

// 每组占几个 warp（不足 32 也算一个）
warpsPerGroup = ceil(threadsPerGroup / 32)

// 四个限制器，各自算出「能驻留几个组」
byWarpSlot  = floor(48 / warpsPerGroup)
byBlockSlot = 24
byRegister  = floor( 4 × floor(16384 / regsPerWarp) / warpsPerGroup )
              // regsPerWarp = ceil(regsPerThread × 32 / 256) × 256   ← 按 256 粒度分配
bySharedMem = floor(102400 / sharedBytesPerGroup)

groups   = min(四者)
occupancy = groups × warpsPerGroup / 48

几个直觉

  • 组太小很吃亏。 numthreads(32,1,1) 每组只有 1 个 warp，24 个 block 槽位用光也只驻留 24 个 warp → 占用率天花板 50%。
  • 寄存器是最常见的瓶颈。 每线程 64 个寄存器时，每 warp 吃 2048 个，一个分区只放得下 8 个 warp（16384/2048）→ 上限 32 warp = 66.7%。复杂 shader 很容易踩到。
  • groupshared 决定组的并存数。 每组用 32 KB，100 KB 只够放 3 个组。
  • 高占用率 ≠ 高性能。 占用率只是"隐藏延迟的能力"。计算密集、访存少、ILP 高的 kernel，50% 占用率也能跑满执行单元；反而为了提高占用率去砍寄存器，可能造成溢出（register spilling）到显存，得不偿失。目标是"够用"，不是"最大"。

05 Memory Coalescing：warp 的形状决定带宽利用率

同一条 load 指令，warp 的 32 条 lane 同时给出 32 个地址。硬件必须把这些地址归并成若干次显存事务 —— 归并得好不好，就是合并访存。

两个硬件事实

Lane

SM 分区里的一条执行道。一个 warp 有 32 条 lane，一条访存指令会同时产生 32 个独立地址。这 32 个地址彼此可以毫无关系（gather），硬件都支持 —— 但代价差别巨大。

Sector

显存 ↔ L2 ↔ L1 之间搬运数据的最小颗粒 = 32 字节，且按 32 B 边界对齐。L1 的一条 cache line 是 128 B = 4 个 sector。你哪怕只要其中 1 个字节，整个 32 B 也必须被搬过来。

合并的过程

32 条 lane 各给一个地址
        ↓
地址合并单元把它们映射到各自所属的 32 B sector
        ↓
去重 → 得到 N 个不同的 sector
        ↓
发出 N 次访存事务，每次搬回 32 B

有效带宽利用率 = (32 × 元素大小) / (N × 32)
场景（每 lane 读 1 个 float = 4 B）sector 数搬运 / 使用效率

形状怎么影响它

回忆第 02 节：warp 里的 32 个线程是 GroupIndex 连续的，而 GroupIndex 沿 X 维增长最快。所以 numthreads 的 X 值直接决定了 warp 在二维上的宽度：

numthreadswarp 0 覆盖每行连续字节（float）sector效率
(64, 1, 1)1 行 × 32 列128 B4100%
(32, 2, 1)1 行 × 32 列128 B4100%
(16, 4, 1)2 行 × 16 列64 B4100%
(8, 8, 1)4 行 × 8 列32 B ← 刚好一个 sector4100%
(4, 16, 1)8 行 × 4 列16 B ← 半个 sector850%
(2, 32, 1)16 行 × 2 列8 B1625%
(1, 64, 1)32 行 × 1 列4 B3212.5%
规律很干净：只要 warp 在每一行上覆盖的连续字节 ≥ 32 B 且对齐，字节效率就是 100%；一旦每行片段小于 32 B，就开始浪费。
换算成建议：numthreads.X × 元素大小 ≥ 32 B。读 float 就要 X ≥ 8，读 float4 就要 X ≥ 2。这就是为什么 (8,8,1)、(16,16,1)、(32,1,1)、(64,1,1) 是最常见的几个配置，而 (1,64,1) 这种基本是性能陷阱。
100% 字节效率之下还有一层差别。 (8,8,1) 和 (32,2,1) 都是 4 个 sector，但前者的 4 个 sector 分散在 4 条不同的 128 B cache line 上，后者集中在 1 条。纯流式扫描（只读一次、无复用）选 (64,1,1) 更省 cache 标签查找；而卷积/滤波这类要读邻域的，方形的 (8,8,1) footprint 更紧凑、L1 复用率高得多，反而更快。

另外，RWTexture2D 与线性 Buffer 的布局不同：纹理在显存里是分块 swizzle 存放的，硬件天然照顾二维局部性，所以对纹理用方形组几乎总是对的；上面这张表严格成立的是按行主序手算下标的线性 Buffer（buf[y*W + x]）。

06 速查

核心公式

总线程        = Dispatch(gx,gy,gz) × numthreads(X,Y,Z)   // 逐维相乘
DispatchThreadID = GroupID × (X,Y,Z) + GroupThreadID
GroupIndex       = gtid.z·X·Y + gtid.y·X + gtid.x       // X 最快
warp 号 / lane 号 = GroupIndex / 32  ,  GroupIndex % 32
occupancy        = 驻留 warp 数 / 48                     // GB202
访存效率         = 32·元素大小 / (sector 数 · 32)

选 numthreads 的四条经验

  1. 总数取 32 的倍数，否则最后一个 warp 有 lane 空转；常用 64 / 128 / 256。
  2. X × 元素大小 ≥ 32 B（读 float 时 X ≥ 8），保证每行片段填满一个 sector。
  3. 别太小：每组 < 64 线程时，24 个 block 槽位会先于 48 个 warp 槽位耗尽，占用率上不去。
  4. 按访问模式选形状：一维流式 → (64,1,1)；二维有邻域复用（模糊、卷积、tile 化） → (8,8,1) / (16,16,1)。
